# Skill length and loading compatibility across Agents

This document records loading differences among ForgeSteward's supported Codex, Claude Code, OpenCode, ZCode, and the DeepSeek Harness filesystem installation adapter, and explains how the repository prevents renewed Skill truncation. Repository editing requirements are in [AGENTS.md](../AGENTS.md#skill-length-and-compatibility-across-agents). [check_skill_limits.py](../scripts/check_skill_limits.py) is the only numeric source for enforced budgets. Length-budget review date: 2026-09-30.

## Repository budgets and organization

These are voluntary repository maintenance budgets, not claims that every Agent uses identical limits. Read enforced values from the script. Any numeric change requires updated rationale, compatibility evidence, and boundary tests here.

| Object | Current maintenance budget | Rationale |
| --- | --- | --- |
| Complete `SKILL.md`, including frontmatter and actual newline bytes | ≤ 6,000 UTF-8 bytes, < 500 lines | Leave 2,000 bytes below the smallest known entry truncation boundary while following Claude's line guidance |
| Each `references/**/*.md` | ≤ 8,000 UTF-8 bytes, < 500 lines | Bound each file read; references are not automatically injected entries, so neither apply 6,000 bytes blindly nor call 8,000 a universal tool limit |
| `description` | Nonempty, ≤ 500 UTF-16 units | Fit DeepSeek Harness's default full-description display boundary and stay below ZCode's 1,024-unit validation boundary; an emoji may use two units |
| `name` | 1–64 ASCII lowercase letters, digits, and single hyphens, matching the Skill directory | Keep common discovery formatting and avoid installed but undiscoverable packages |

Starting with source target `0.2.15`, the shared description budget tightened from 1,024 to 500 UTF-16 units. This is a repository maintenance choice, not a claim that a configurable discovery default is a hard limit for all Agents. New and edited descriptions must pass the same check; do not exempt existing Skills or ask users to increase client settings. The former `prepare-work` description was 707 units, truncating trailing purpose/exclusion details in default discovery. It was shortened to 487 units while detailed queue, count, authorization, and output rules remained in the original body/references. See [Issue #39](https://github.com/philfanzhou/ForgeSteward/issues/39).

Repository `name` and `description` fields use single-line text without quotes, comments, aliases, or folding. The validator rejects unsupported syntax rather than counting the `>` in `description: >` as an entire description. It is not a general YAML parser; add parsing and multi-Agent validation before introducing other forms.

Skill entry points retain purpose, authorization, stage navigation, and output contracts. Put detailed stage rules in bundled `references/`, using relative Markdown links to specify when they must be read. Paths are relative to the installed Skill directory. Cross-file references must not depend on files outside the repository or another plugin's installation. Do not hide rules in `assets/`, script strings, or unchecked Markdown to bypass budgets. Large non-instructional data should be task data processed selectively by tools.

Budgets are ceilings, not targets. Descriptions should lead with purpose and triggers, leaving detailed steps in the body. References may be split further by stage, but existing guarantees cannot become optional or be replaced with summaries. When Skill or reference reads are truncated, reread in chunks to the end. This does not apply to CI logs, test output, or other tool results, which use the selective-reading guidance in `execute-work`, `fix-feedback`, and `review-and-merge`'s bundled `references/ci.md`. For a missing file, identify its exact path and stop affected operations. After compaction, reread missing current-stage rules. Each independently installed Skill carries these runtime requirements; static checks do not prove model compliance.

## Automated checks and local use

```bash
python3 scripts/check_skill_limits.py --check
python3 -m unittest discover -s tests -v
```

The checker needs neither network access nor third-party Python packages and writes no files. It traverses every plugin and future Skill automatically, reporting actual bytes, lines, and budgets per file. It reports total description size for diagnosis without calling that total any client's discovery-list budget. Exceeded limits, invalid metadata, empty Skill sets, missing/out-of-bounds references, and unreachable references return nonzero status with the file and corrective direction.

CI runs the same command in Linux, macOS, and Windows installer checks. Unit tests cover ASCII/CJK descriptions at 500/501 units, emoji at 250/251 characters, rejection of mixed text at exactly 501 units, nonzero CLI exit for oversized descriptions, raw CRLF bytes, line counts, exact boundaries and one-unit overflow, duplicate/multiline metadata, missing/out-of-bounds/cyclic references, automatic future-plugin inclusion, and read-only CLI exit status. Installer tests still compare every resource byte for byte to prevent omitted packaging after splits. No extra local Git hook is required; PR checks catch missed local runs.

Real OpenCode discovery tests compare all six loaded bodies with source; CI remains pinned to `1.18.30`. Local `2.0.16` removed the test's `debug skill --pure` command, so run the test only with an explicitly compatible `FORGESTEWARD_OPENCODE`. A V1 pass is not proof of real V2 loading. ZCode desktop `3.14.3`'s bundled CLI `0.16.9` checked all six complete bodies, resource paths, and `truncated` in a temporary plugin directory, plus temporary-Skill boundaries at 100,000/100,001 bytes and 512/513 emoji descriptions. Neither test calls a model or changes user plugins/global configuration. See [ZCode rerun commands](zcode.md#verification-records-and-reruns).

On 2026-09-30, the actual `FileSystemSkillProvider` from DeepSeek Harness desktop `0.2.0-rc.2` discovered six Skills in an isolated temporary project. Every complete body, `resourceBase`, and resource matched byte for byte, including discovery from a project subdirectory. The six earlier descriptions measured 332, 394, 305, 707, 321, and 335 UTF-16 units; only prepare-work's description changed. A directory-package loading probe also read a full 120,003-byte UTF-8 body and 1,100-unit description, showing that 500 is not a provider body-reading limit; it does not show the model receiving that body. Actual installed-package source separately verified formatter boundaries at 500/501, emoji, and mixed characters. All six descriptions displayed in full in the default catalog. The real rule loader read repository `AGENTS.md` without omission or truncation. No user configuration, installed Skills, or model calls were changed or used.

See [installation maintenance](deepseek-installer.md) for DeepSeek Harness's managed lifecycle and reruns, corresponding to [Issue #40](https://github.com/philfanzhou/ForgeSteward/issues/40). On 2026-09-30 the actual `0.2.0-rc.2` provider reverified full bodies, resourceBase, all resource digests, candidate ranking, Git worktree markers, and post-uninstall rediscovery in isolated project/user scopes. Standard-library lifecycle regressions run in three-OS CI. Without an explicit real runtime, skip and do not count it as a pass. Native Windows Harness remains unverified. The maintainer manually ran `work-cycle` on local `0.2.0-rc.2` and verified delegation, closing [Issue #41](https://github.com/philfanzhou/ForgeSteward/issues/41). That real-runtime manual check is not an automated repository CI regression. Desktop GUI, model compaction recovery, and other clients/models/configurations remain uncertified. Static availability of subagent components and tool settings is not an end-to-end work-cycle guarantee for every environment.

Codex truncation was checked against a fixed upstream commit. Read-only prompt rendering with local CLI `0.157.1` confirmed all six entry points can appear in discovery, not body injection. Claude Code was checked against official guidance; local `2.1.283` passed `plugin validate --strict` for all six plugins, which does not prove the model received complete bodies. No end-to-end model invocation or compaction-recovery test is claimed here for Codex or Claude Code. ZCode desktop GUI marketplace lifecycle remains outside CLI verification.

When changing a verified Agent version or adding an Agent, first recheck official docs and available loading implementations. Record whether each limit concerns entry points, metadata lists, tool output, or context recovery, with units and configurability. Run boundary probes in temporary directories when needed. Tighten budgets and reorganize oversized Skills for newly stricter limits; looser limits do not automatically increase entry budgets. Retain verification records here and in release inputs without overwriting historical evidence.

No static length check guarantees that every user configuration, other installed Skill, tool wrapper, model, and entire conversation stays within context limits. These checks prevent growth regressions in entries and resources this repository controls. Smaller personal budgets, crowded dynamic discovery lists, and missing post-compaction rules still require client warnings and the Skills' complete-reading requirements.
