# ForgeSteward v0.2.1

A compatibility-fix release with consistent display names and upgrade, uninstallation, and old-version cleanup instructions for three Agents. The project is still in the early `0.x` stage. This file is release input; completion is confirmed by the remote Tag of the same name and the [GitHub Release](https://github.com/philfanzhou/ForgeSteward/releases/tag/v0.2.1). The full commit SHA, release-preparation PR, and final main-branch CI links are recorded in the Release body rather than recursively embedding this file's own SHA.

The marketplace remains `forge-steward`, and the repository Tag pins the marketplaces, installer, and documentation. Arbitrary combinations of historical plugin versions and standalone npm/PyPI/NuGet packages are not provided.

## Changes and migration

- [PR #8](https://github.com/philfanzhou/ForgeSteward/pull/8): standardized Codex display names for the four plugins and Skills, added metadata regression tests, and removed the hardcoded previous package version from installer tests.
- [PR #9](https://github.com/philfanzhou/ForgeSteward/pull/9): moved Codex, Claude Code, and OpenCode upgrade instructions near the start of the README, with scope, cache, leftover, and rollback limitations.
- Release preparation updates the recommended Tag, pinned-version examples, and this mapping table. The [v0.2.0 historical notes](v0.2.0.md) remain unchanged.
- Upgrading from `v0.2.0` does not change installation IDs, Skill invocation names, default prompts, Skill bodies, or the installer implementation. Display labels and invocation identifiers are distinct; existing invocation names need no rewriting.

Select `v0.2.1` using the [README upgrade steps](../../README.md#upgrade-and-keep-only-the-selected-version) or [fixed-version guide](../versioned-installation.md). For Codex/Claude Code, first record and remove the original installation, replace the marketplace ref, then restore the original subset and scope. For OpenCode, select the source Tag and explicitly update. Check versions and sources in a new session, and back up user changes first. Refreshing a marketplace pinned to `v0.2.0` does not upgrade it to this version. To roll back, use the same procedure to select `v0.2.0`; old Tags are not moved, and work already performed by Skills is not automatically undone.

## Validation and exclusions

- The 46 standard-library tests cover installation, updates, replacement of obsolete files, uninstallation, leftover protection, and display-name/identity/version consistency for all four plugins. Locally on macOS, 44 passed; the Windows junction case and unconfigured real OpenCode case were explicitly skipped. Consult the Release record for final three-platform CI and real discovery/uninstallation results with pinned OpenCode `1.18.30`.
- Strict format validation passed for the four Claude plugins and the marketplace. PR #8 records Codex plugin and Skill format validation. Installation/discovery evidence and display metadata checks do not constitute end-to-end validation of rendering or model behavior in every desktop client.
- Claude Code `2.1.269` used separate temporary configuration and plugin directories to install four `0.2.1` packages through a local marketplace. Installed copies were compared file by file with the release source, then uninstalled, and the installation list was confirmed empty. This does not replace remote Tag retrieval or interactive-session validation.
- In a temporary project, the OpenCode installer first installed the four `v0.2.0` Skills, then ran `update --all` from the release source. All four showed `0.2.1 (matches checkout)`; all were then uninstalled with no candidate leftovers in the selected target. Real user installations were not touched.
- Existing user installations are unchanged. Actual Codex desktop selector display, search, and old-session refresh still require confirmation in a new session after installation; this release does not promise immediate refresh in every client.
- Immediate absence of all disk leftovers is not guaranteed. Other scopes, manual copies, retired names, and Claude caches awaiting background cleanup require separate checks. No bulk deletion of shared caches is provided.
- No native Windows OpenCode runtime validation was performed. Existing exclusions for power loss, forced termination, and malicious concurrent writes remain.
