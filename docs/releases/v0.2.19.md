# v0.2.19

This file is release input for `v0.2.19`. Publication is complete only when both the matching remote annotated Tag and a non-draft GitHub Release exist.

This release addressed one goal: reduce idle waiting, rework, and duplicate checks caused by work-cycle rules while keeping the same workload. Review standards, merge conditions, and the maximum of three repairs per PR remained unchanged.

## Changes

- **Remove rework and stalls** ([PR #62](https://github.com/philfanzhou/ForgeSteward/pull/62), [Issue #59](https://github.com/philfanzhou/ForgeSteward/issues/59)):
  - After pushing, fix-feedback checks the CI triggered by that push and fixes failures caused by its changes within the same repair, without counting another repair.
  - Review sends conflicts and branches stale under an up-to-date requirement to repair for main synchronization. Pushes solely for synchronization do not consume a repair round.
  - Review, repair, and implementation wait for CI at most twice the slowest of the repository's recent successful runs of that check, or 30 minutes when history is unavailable. Process other items first, then return.
  - execute-work records inability to proceed and unblock conditions on the original Issue; prepare-work reuses that conclusion next round while conditions remain unchanged.
  - work-cycle subagents no longer stop to wait for user answers; they record questions on the Issue and in their return.
- **Remove duplicate checks** ([PR #63](https://github.com/philfanzhou/ForgeSteward/pull/63), [Issue #60](https://github.com/philfanzhou/ForgeSteward/issues/60)):
  - Rereview and repair reuse conclusions when code, feedback, checks, and relevant mainline contents are unchanged, reconfirming only checks, approvals, conflicts, and protection.
  - Within one run, later prepare-work cycles reuse earlier security-alert checks, initial screening, and blocker rechecks, inspecting only changes.
  - Final review reuses repair's per-commit audit. Reviewers do not rerun locally checks already passed by CI on the same commit. Read the automatic post-merge branch-deletion setting only once per invocation.
  - The work-cycle orchestrator stores only conclusion summaries and evidence locations, and checks only the Issues/PRs touched by the completed stage.
- **Let completed items advance early** ([PR #64](https://github.com/philfanzhou/ForgeSteward/pull/64), [Issue #61](https://github.com/philfanzhou/ForgeSteward/issues/61)):
  - When background subagents are supported, review can start as soon as execution hands off a PR. Review/repair can overlap later implementation and the next preparation cycle. Implementation and preparation themselves still run one after the other in this release.
  - Avoid interference: one PR belongs to one stage at a time; stages use separate workspaces; implementation branches from latest remote main and synchronizes again before pushing; post-merge cleanup preserves other stages' directories; only the orchestrator writes shared progress.
  - Rules live in new work-cycle `references/concurrency.md`. Unsupported runtimes retain serial stages.

## Upgrade steps

Skill names, invocation, installation, and configuration did not change; no data migration was needed. Update installed plugins using [fixed-version installation, upgrades, and rollback](../versioned-installation.md). All six must use the same version for work-cycle.

Two behavioral changes:

- Repair synchronizes main on the original branch, using merge when force pushes are prohibited. Main-sync merge commits may appear in PRs.
- With background subagents, work-cycle runs multiple stages at once and multiple PRs' CI may queue concurrently.
