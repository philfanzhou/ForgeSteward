# v0.2.19

本文件是 `v0.2.19` 的发布输入。远端同名附注 Tag 和非 draft GitHub Release 都存在，才算发布完成。

这一版只解决一件事：用 work-cycle 跑完整流程时，在工作量不变的前提下，减少因为规则本身造成的白等、返工和重复检查。审查标准、合并条件和“每个 PR 最多改 3 次”的上限都没变。

## 改了什么

- **堵住返工和卡死**（[PR #62](https://github.com/philfanzhou/ForgeSteward/pull/62)，对应 [Issue #59](https://github.com/philfanzhou/ForgeSteward/issues/59)）：
  - fix-feedback 推送后自己检查这次触发的 CI，本次修改造成的失败当场修好，不算新的一次修改。
  - 与主线冲突、或仓库要求分支保持最新而已落后的 PR，审查交给修复阶段同步主线；只为同步主线的推送不占修改次数。
  - 审查、修复、实现等 CI 时，等待上限取该仓库同一检查最近几次成功运行中最慢一次的 2 倍，查不到历史时 30 分钟；先处理别的项，最后回来看。
  - execute-work 把做不了的原因和解除条件写回原 Issue；prepare-work 下一轮看到条件没变就沿用，不重复调查。
  - work-cycle 派出的子 Agent 不再停下来等用户回答，问题写进 Issue 和返回结果。
- **去掉重复检查**（[PR #63](https://github.com/philfanzhou/ForgeSteward/pull/63)，对应 [Issue #60](https://github.com/philfanzhou/ForgeSteward/issues/60)）：
  - 代码、意见、检查和相关主线都没变的 PR，复审和修复沿用上次结论，只重新确认检查、审批、冲突和分支保护。
  - 同一次运行里，prepare-work 后几轮沿用前面的安全告警、快速过一遍和受阻任务复查结果，只补查有变化的部分。
  - 最后一次审查复用修复阶段记录的逐 commit 审计；审查者不在本地重跑 CI 已在同一提交通过的检查；“合并后自动删分支”设置每次调用只读一次。
  - work-cycle 编排只保存结论摘要和证据位置，每个阶段结束只核对该阶段动过的 Issue 和 PR。
- **已完成的项先往下走**（[PR #64](https://github.com/philfanzhou/ForgeSteward/pull/64)，对应 [Issue #61](https://github.com/philfanzhou/ForgeSteward/issues/61)）：
  - 运行环境支持后台子 Agent 时，实现阶段每交出一个 PR 就可以开始审查；审查与修复的循环可以和后续实现、下一轮准备同时进行。实现和准备仍然一前一后。
  - 防止互相踩到：一个 PR 同一时间只归一个阶段；各阶段用独立工作目录；实现只从远端最新主线开分支，推送前再同步；合并后清理不碰其他阶段的目录；共享进度记录只由编排 Agent 写。
  - 规则在 work-cycle 新文件 `references/concurrency.md`。运行环境不支持时退回原来逐阶段串行的做法。

## 升级需要做什么

技能名、调用方式、安装方式和配置都没变，没有数据迁移。按[固定版本安装、升级与回退](../versioned-installation.md)更新已安装的插件即可；用 work-cycle 时六个插件要升到同一版本。

行为上有两点和以前不同：
- 修复阶段会在原分支上同步主线（不允许强推时用 merge），PR 里会出现同步主线的合并提交。
- 运行环境支持后台子 Agent 时，work-cycle 会同时运行多个阶段，多个 PR 的 CI 可能同时排队。

## 验证情况

- 本地测试 148 项：142 项通过，6 项因环境不适用而跳过。
- 技能长度检查、版本一致检查（`sync_marketplace.py --check`）、`git diff --check` 通过。
- 各 PR 的三个系统安装器检查和 discovery 检查全部通过。

没验证的：这些改动都是规则文字，没有在真实仓库里端到端跑过，尤其是同时运行多个阶段；不能保证模型每次都照做。`fix-feedback/SKILL.md` 在 Windows 换行下是 5984/6000 字节，接近上限，以后在这个入口加内容需要先挪到 `references/`。
