# ForgeSteward v0.2.11

A unified patch release: prepare-work prioritizes baseline Issues when filling batches, rechecks baseline blockers each round, and checks parents whose children are all closed. The four Skills handling Issues consolidate adjacent defects into shared records to reduce new Issues. This file is release input and does not itself prove publication. Before installing, confirm that both the remote `v0.2.11` Tag and a non-draft [GitHub Release](https://github.com/philfanzhou/ForgeSteward/releases/tag/v0.2.11) exist. The actual full commit SHA, release PR, and final main-branch CI links are recorded in the Release body.

## Changes since v0.2.10

From [PR #33](https://github.com/philfanzhou/ForgeSteward/pull/33).

### prepare-work

- Distinguish baseline work from additions during the cycle: Issues already open at the cycle baseline are baseline work. Tasks split from them, and new tasks created and linked as real prerequisites for baseline work, inherit baseline status. Carry the cycle baseline across rounds using the tracker or previous handoff; rerunning does not reset it.
- Fill batches by tier: baseline tasks, with mainline work first → severe risks added during the cycle that need immediate action → other additions during the cycle. Finish one tier before preparing the next. If selection exceeds the limit, retain higher-tier items first, and output the final list by tier. Removed the goal of returning as many ready items as possible within the limit.
- Added baseline-blocker rechecks: do not exclude baseline candidates during classification merely because of a blocker marker or the previous round's conclusion. Check actual dependencies and release conditions each round, removing stale blockers. With authorization, change relationships expressing scheduling order alone to nonblocking. Complete preparation this round even for baseline items dependent on unmerged prerequisites. When maintainer action is needed, state the action, responsible role, and baseline tasks it can unblock.
- Consolidate adjacent findings: group similar defects in one Issue or append them to an existing similar Issue. Record optional improvements, speculative risks, and tidiness concerns only in the original Issue. Readiness no longer requires a new Issue for each adjacent finding.
- During classification, check parents whose children are all closed. When evidence satisfies acceptance criteria, close them within authorization and list them separately. Tasks split from remaining gaps inherit baseline status.
- Record the cycle baseline, remaining and selected baseline counts, newly created Issue count this round, selected cycle-addition count, and completed-parent count in the existing tracker.
- Added scenarios P22–P28.

### execute-work, review-and-merge, and fix-feedback

- Consolidate similar independent existing defects by appending evidence to an existing or shared Issue. Create a new one only for a confirmed, reproducible, independent defect with no similar record. Record optional improvements only in the original Issue or Change Request.

## Migration

- There are no incompatible changes; installation IDs, invocation methods, and the final output format are unchanged.
- prepare-work's final list may be shorter than before: additions during the cycle no longer fill places before baseline candidates are handled. Progress updates explain why baseline work did not fill the batch.
- On first use of this version in a repository without a cleanup-cycle record, prepare-work establishes the cycle baseline at the current freeze time and treats all previously open Issues as baseline work.
- When explicitly invoked without write restrictions, prepare-work may remove stale blocker markers, make scheduling-only dependencies nonblocking, and close parents whose acceptance criteria are met. Specify read-only operation when invoking it if needed.

## Installation, upgrade, and rollback

Use these commands only after confirming this version has been released, in a new environment without a marketplace of the same name. For an existing installation, follow the [version switching and cleanup guide](../versioned-installation.md) to record the selected subset, scope, and source; uninstall old copies, replace the marketplace ref, and reinstall the original subset. Do not add the same marketplace twice or edit caches directly. The guide's `v0.2.1` / `find-work` examples are historical; for this version, replace both with `v0.2.11` and the actual plugin names in the table above.

Example for a new Codex environment (install other plugins individually using the table above):

```bash
codex plugin marketplace add philfanzhou/ForgeSteward --ref v0.2.11
codex plugin add prepare-work@forge-steward
codex plugin list
```

Example for a new Claude Code environment:

```text
/plugin marketplace add philfanzhou/ForgeSteward@v0.2.11
/plugin install prepare-work@forge-steward
```

For OpenCode, use a separate snapshot and replace the absolute placeholder paths below. Run installation commands from the target repository you want to maintain:

```bash
git clone --branch v0.2.11 https://github.com/philfanzhou/ForgeSteward.git /absolute/path/ForgeSteward-v0.2.11
git -C /absolute/path/ForgeSteward-v0.2.11 rev-parse HEAD
python3 /absolute/path/ForgeSteward-v0.2.11/scripts/opencode.py install --all --project .
python3 /absolute/path/ForgeSteward-v0.2.11/scripts/opencode.py status --all --project .
```

Before installing, confirm that the checkout SHA matches the Release. For an existing installation, use `update --all --project .` from the same snapshot's installer, or specify the recorded subset and `--user`, instead of repeating `install`. If local customizations trigger protection, back them up and inspect them before deciding what to do; do not force an overwrite.

For ZCode, follow [fixed versions and rollback](../zcode.md#fixed-versions-and-rollback) to add the root of the verified, separate `v0.2.11` checkout as a local marketplace, select the plugin subset, and confirm the installed versions. Before switching, save the original source, uninstall old plugins, and remove the old marketplace. Do not directly reuse Codex's `--ref` or Claude's `@tag` syntax.

Upgrading from `v0.2.10`, `v0.2.9`, `v0.2.8`, or `v0.2.7` requires only switching versions, with no additional migration. From `v0.2.6` or earlier, first read the [v0.2.7 migration notes](v0.2.7.md#migration): check-workflow's deletion behavior is an incompatible change. From `v0.2.1` or earlier, first remove retired `find-work` and install `prepare-work` instead. Confirm every selected plugin is `0.2.11`. Roll back with the same procedure by selecting the retained `v0.2.10`; rollback does not undo project changes, merges, or hosting-platform operations already performed.
