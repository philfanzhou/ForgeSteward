# ForgeSteward v0.2.4

A unified patch release with fixes to stage handoffs in the five-Skill adoption check. This file is release input and does not itself prove publication. Before installing, confirm that both the remote `v0.2.4` Tag and a non-draft [GitHub Release](https://github.com/philfanzhou/ForgeSteward/releases/tag/v0.2.4) exist. The actual full commit SHA, release PR, and final main-branch CI links are recorded in the Release body.

## Changes since v0.2.3

- [PR #14](https://github.com/philfanzhou/ForgeSteward/pull/14): check-workflow adoption checks now cover separation of preparation and implementation, handoffs recoverable independently from the original Issue, explicit lists and full-batch completion, cross-session state, and safe cleanup. Added limited scenarios F01–F11.
- A general chat handoff cannot replace the preparation stage's required persistence in the original Issue. In read-only mode, an existing complete handoff still allows an actual readiness check.
- Skills remain independently usable, with no mandatory preparation prerequisite or automatic chaining. Conflicts with old rules are reported for a migration decision, without overwriting original rules or incorrectly renaming historical identifiers.
- Added this unified version and release entry point, corrected the README's description of published `v0.2.3` as unreleased, and retained clearly labeled historical `v0.2.1` installation examples.

## Installation, upgrade, and rollback

Use these commands only after confirming this version has been released, in a new environment without a marketplace of the same name. For an existing installation, follow the [version switching and cleanup guide](../versioned-installation.md) to record the selected subset, scope, and source; uninstall old copies, replace the marketplace ref, and reinstall the original subset. Do not add the same marketplace twice or edit caches directly. The guide's `v0.2.1` / `find-work` examples are historical; for this version, replace both with `v0.2.4` and the actual plugin names in the table above.

Example for a new Codex environment (install other plugins individually using the table above):

```bash
codex plugin marketplace add philfanzhou/ForgeSteward --ref v0.2.4
codex plugin add check-workflow@forge-steward
codex plugin add prepare-work@forge-steward
codex plugin add execute-work@forge-steward
codex plugin list
```

Example for a new Claude Code environment:

```text
/plugin marketplace add philfanzhou/ForgeSteward@v0.2.4
/plugin install check-workflow@forge-steward
/plugin install prepare-work@forge-steward
/plugin install execute-work@forge-steward
```

For OpenCode, use a separate snapshot and replace the absolute placeholder paths below. Run installation commands from the target repository you want to maintain:

```bash
git clone --branch v0.2.4 https://github.com/philfanzhou/ForgeSteward.git /absolute/path/ForgeSteward-v0.2.4
git -C /absolute/path/ForgeSteward-v0.2.4 rev-parse HEAD
python3 /absolute/path/ForgeSteward-v0.2.4/scripts/opencode.py install --all --project .
python3 /absolute/path/ForgeSteward-v0.2.4/scripts/opencode.py status --all --project .
```

Before installing, confirm that the checkout SHA matches the Release. For an existing installation, use `update --all --project .` from the same snapshot's installer, or specify the recorded subset and `--user`, instead of repeating `install`. If local customizations trigger protection, back them up and inspect them before deciding what to do; do not force an overwrite.

For ZCode, follow [fixed versions and rollback](../zcode.md#fixed-versions-and-rollback) to add the root of the verified, separate `v0.2.4` checkout as a local marketplace, select the plugin subset, and confirm the installed versions. Before switching, save the original source, uninstall old plugins, and remove the old marketplace. Do not directly reuse Codex's `--ref` or Claude's `@tag` syntax. Check manually imported copies, other scopes, and legacy caches individually using the [uninstallation guide](../zcode.md#uninstalling-and-keeping-only-the-target-version); do not delete content shared with other plugins.

Upgrading from `v0.2.3` does not change installation IDs or invocation methods. From `v0.2.1` or earlier, first remove retired `find-work`, install `prepare-work` instead, and add `execute-work` as needed; there is no old-name alias. OpenCode can use `uninstall find-work --project .` in the new installer to clean up the old managed item before installing the new name. Selecting the preparation Skill in a new session runs it directly; the execution Skill requires an explicit list, such as `$forge-steward-execute-work #123, #145`. See the [README](../../README.md#calling-the-skills) for invocation details.

Confirm that every selected plugin is `0.2.4`; do not retain an old package merely because its Skill body did not change. Remove only copies confirmed to belong to an unused old version, preserving local customizations and other environments. Roll back with the same procedure by selecting the retained `v0.2.3` and checking its version and actual content. Upgrading Skills does not automatically migrate consumer-repository rules, and rollback does not undo project changes or hosting-platform operations already performed.

## Validation and exclusions

Before release, run the full unit suite, unified-version, marketplace, resource, and format validation, relative-link checks, and isolated installation checks for affected packages. The installer checks on all three operating systems and the pinned OpenCode discovery check must pass for both the PR and final main commit. Record actual results in the PR / Release.

check-workflow's [F01–F11 scenarios](../check-workflow-scenarios.md#five-skill-stage-handoff-revision) are manual rule walkthroughs, not independent Agent behavior evaluations. ZCode remains a development preview: discovery and body reading in desktop 3.11.2 / bundled CLI 0.16.5 do not establish validation of GUI marketplace installation, update, rollback, uninstallation, or model behavior. Codex / Claude package structure and isolated installations likewise do not establish end-to-end validation for all desktop versions.

This release distributes only a Git snapshot and GitHub's automatic source archives, with no separate build packages. It does not change real local installations or user configuration.
