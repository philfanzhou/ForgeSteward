## 新编排技能

显式调用 `forge-steward-work-cycle` 即请求完整交付；唯一可选输入是正整数工作周期数，默认 5。每个阶段由独立子 Agent 完整加载并执行原技能；没有子 Agent 能力或缺少同版本阶段技能时，不退化成编排 Agent 在自身上下文执行。`prepare-work` 返回 `[]` 时提前结束。一个 Issue 或 Change Request 暂停不阻断其他独立工作；合并仍须满足原验收、必要检查、审批和分支保护。

`check-workflow` 只在启动时做一次低频判定，不加入每周期：目标仓库没有本地运行记录时执行；已完成运行后，仅在统一版本变化且距上次运行至少 168 小时时再次自动执行。未完成运行在 168 小时后可重试。普通提交、文件变化和 PR/MR 事件不触发。记录位于目标仓库 Git common dir 的 `forge-steward/check-workflow.json`，不加入项目提交；新克隆没有共享缓存，会执行一次首次检查。`check-workflow` 本身仍只删除项目中的重复规则。

## 第三次修复后的终审

`fix-feedback` 在第 3 次修复推送后停止自动修复，交由 `review-and-merge` 对该 head 进行一次终审。满足全部门禁时合并；仍有范围内必修问题时记录 head 和证据，仅暂停该 Change Request，之后不自动要求第 4 次修复或重复审查。只等待 CI 或审批时按平台等待处理，不把等待误判为代码失败。Review 往返数沿用平台时间线和交接记录，不随新工作周期归零。历史上“满 3 轮直接跳过审查”的行为因此改变；同版本技能应一起升级，不能混用旧审查规则与新编排规则。

## 安装、验证与边界

六个插件仍分别安装，完整编排要求同版本五个阶段插件、可用的子 Agent 创建与等待能力，以及各仓库正常的托管平台权限。OpenCode 安装器会复制新技能的完整目录及缓存判定脚本；单独安装编排插件不会自动安装其他五项。当前会话之外的定时重启须由外部调度提供，技能自身不保证后台持续运行。

发布前运行 `python3 scripts/check_skill_limits.py --check`、`python3 scripts/sync_marketplace.py --check`、`python3 -m unittest discover -s tests -v` 和 `git diff --check`；实际结果应记录在交付说明。有限场景见 [编排技能场景验收](../work-cycle-scenarios.md)。单元测试和规则走查不能证明所有 Agent/模型的子 Agent 行为一致，发布前还需对可用客户端做安装及真实调用验证；未验证平台须如实说明。
