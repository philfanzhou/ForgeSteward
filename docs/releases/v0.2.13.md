## New orchestration Skill

Explicit invocation of `forge-steward-work-cycle` requests full delivery. Its only optional input is a positive integer count of work cycles, defaulting to 5. An independent subagent fully loads and executes the original Skill for each stage. If subagent support or same-version stage Skills are missing, the orchestrator does not fall back to executing stages in its own context. A `[]` result from `prepare-work` ends the run early. Pausing one Issue or Change Request does not block independent work. Merging still requires original acceptance criteria, required checks, approvals, and branch protection to be satisfied.

`check-workflow` makes one low-frequency decision at startup rather than running in every cycle. It runs when the target repository has no local run record. After a completed run, it runs automatically again only when the unified version changes and at least 168 hours have elapsed. An incomplete run can be retried after 168 hours. Ordinary commits, file changes, and PR/MR events do not trigger it. The record lives at `forge-steward/check-workflow.json` in the target repository's Git common dir and is not committed. A fresh clone has no shared cache and receives an initial check. `check-workflow` itself still only removes duplicate project rules.

## Final review after the third repair

`fix-feedback` stops automatic repair after the third repair push and hands that head to `review-and-merge` for one final review. Merge if all gates pass. If required in-scope problems remain, record the head and evidence and pause only that Change Request; do not automatically request a fourth repair or repeat the review. Waiting only for CI or approval is handled as a platform wait, not a code failure. Review round counts carry forward from the platform timeline and handoff records, without resetting for a new work cycle. This changes the historical behavior of skipping review after three rounds. Upgrade same-version Skills together; do not mix old review rules with new orchestration rules.

## Installation, validation, and limitations

The six plugins remain separately installable. Full orchestration requires the five stage plugins at the same version, usable subagent creation and waiting capabilities, and normal hosting-platform permissions for each repository. The OpenCode installer copies the new Skill's complete directory and cache-decision script. Installing only the orchestration plugin does not install the other five. Scheduled restarts beyond the current session require an external scheduler; the Skill itself does not guarantee continuous background operation.

Before release, run `python3 scripts/check_skill_limits.py --check`, `python3 scripts/sync_marketplace.py --check`, `python3 -m unittest discover -s tests -v`, and `git diff --check`, recording actual results in delivery notes. ZCode bundled CLI `0.16.9` validated discovery, complete body reading, and length boundaries for six Skills in a temporary workspace. Pinned OpenCode `1.18.30` validated discovery and body consistency for all six. See [orchestration Skill acceptance scenarios](../work-cycle-scenarios.md) for limited scenarios. These checks and rule walkthroughs do not prove consistent subagent behavior across all Agents/models and do not cover ZCode desktop marketplace installation or model behavior. State unverified areas accurately.
