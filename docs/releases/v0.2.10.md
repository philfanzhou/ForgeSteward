A unified patch release: prepare-work continues filling the batch through splitting, lengthy investigations, and resolved blockers. review-and-merge consistently removes local source branches after merging and prompts the user to decide when the repository has not enabled automatic source-branch deletion. ## Changes since v0.2.9

### prepare-work

From [PR #30](https://github.com/philfanzhou/ForgeSteward/pull/30).

- Tasks split from frozen candidates during this run under the task-granularity rules inherit frozen status and are assessed individually. Trackers remain ineligible, as do tasks still depending on unmerged prerequisites in a dependency chain.
- Before detailed preparation, perform a lightweight read-only classification of the entire frozen list. Candidates with an open implementation, trackers, candidates depending on unmerged prerequisites, and candidates with a recorded real external blocker whose release conditions are unchanged are immediately ineligible. Classification does not replace the gate and must not exclude candidates because their estimated effort is high.
- If a non-mainline candidate requires several lengthy investigation rounds, save evidence and the next action, then advance later candidates first. Return to it if the batch is not full; the final list still follows the prescribed order.
- Advance other candidates while mainline work waits for lengthy results such as CI, environment builds, or external replies. Waiting neither removes the obligation to keep advancing mainline work nor classifies it as externally blocked.
- The pre-output recheck now includes unselected frozen candidates whose blocker-release conditions were met during this run. The selection limit still applies.
- Removed “one or two” wording; frontmatter `description` and the default prompt now express filling the batch within the default limit or user-specified count.
- Tests: the real OpenCode discovery test now writes output to a temporary file to avoid macOS pipe truncation at 65536 bytes.

### review-and-merge

From [PR #31](https://github.com/philfanzhou/ForgeSteward/pull/31).

- After merging, remove the merged Change Request's local source branch and dedicated worktree, regardless of whether they were created in the current run. Preserve and report them if there are uncommitted changes or the local head differs from the merged head.
- Added remote source-branch checks: read whether the repository automatically deletes source branches after merging, then read back remote branch state. If the setting is disabled or unreadable, or the branch remains, do not independently delete the remote branch or change repository settings. After merging, inform the user of retained branches and the setting state so they can choose automatic deletion or manual removal. This notice does not pause the frozen list and is summarized in the output.
- When the user explicitly authorizes remote-branch deletion in the current invocation, delete only merged source branches in the same repository whose remote heads match the merged Change Requests.

## Migration

- There are no incompatible changes; installation IDs, invocation methods, and the final output format are unchanged.
- review-and-merge now removes merged local source branches with no unique work even when they were not created in this run. Specify any branch that must be retained when invoking the Skill.
- When the repository has not enabled automatic source-branch deletion after merging, review-and-merge adds a notice to its output. Enable the corresponding hosting-platform setting if automatic cleanup is desired.

## Installation, upgrade, and rollback

Use these commands only after confirming this version has been released, in a new environment without a marketplace of the same name. For an existing installation, follow the [version switching and cleanup guide](../versioned-installation.md) to record the selected subset, scope, and source; uninstall old copies, replace the marketplace ref, and reinstall the original subset. Do not add the same marketplace twice or edit caches directly. The guide's `v0.2.1` / `find-work` examples are historical; for this version, replace both with `v0.2.10` and the actual plugin names in the table above.

Example for a new Codex environment (install other plugins individually using the table above):

```bash
codex plugin marketplace add philfanzhou/ForgeSteward --ref v0.2.10
codex plugin add review-and-merge@forge-steward
codex plugin list
```

Example for a new Claude Code environment:

```text
/plugin marketplace add philfanzhou/ForgeSteward@v0.2.10
/plugin install review-and-merge@forge-steward
```

For OpenCode, use a separate snapshot and replace the absolute placeholder paths below. Run installation commands from the target repository you want to maintain:

```bash
git clone --branch v0.2.10 https://github.com/philfanzhou/ForgeSteward.git /absolute/path/ForgeSteward-v0.2.10
git -C /absolute/path/ForgeSteward-v0.2.10 rev-parse HEAD
python3 /absolute/path/ForgeSteward-v0.2.10/scripts/opencode.py install --all --project .
python3 /absolute/path/ForgeSteward-v0.2.10/scripts/opencode.py status --all --project .
```

Before installing, confirm that the checkout SHA matches the Release. For an existing installation, use `update --all --project .` from the same snapshot's installer, or specify the recorded subset and `--user`, instead of repeating `install`. If local customizations trigger protection, back them up and inspect them before deciding what to do; do not force an overwrite.

For ZCode, follow [fixed versions and rollback](../zcode.md#fixed-versions-and-rollback) to add the root of the verified, separate `v0.2.10` checkout as a local marketplace, select the plugin subset, and confirm the installed versions. Before switching, save the original source, uninstall old plugins, and remove the old marketplace. Do not directly reuse Codex's `--ref` or Claude's `@tag` syntax.

Upgrading from `v0.2.9`, `v0.2.8`, or `v0.2.7` requires only switching versions, with no additional migration. From `v0.2.6` or earlier, first read the [v0.2.7 migration notes](v0.2.7.md#migration): check-workflow's deletion behavior is an incompatible change. From `v0.2.1` or earlier, first remove retired `find-work` and install `prepare-work` instead. Confirm every selected plugin is `0.2.10`. Roll back with the same procedure by selecting the retained `v0.2.9`; rollback does not undo project changes, merges, or hosting-platform operations already performed.
