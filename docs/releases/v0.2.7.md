# ForgeSteward v0.2.7

A unified patch release: workflow policy moves into the four working Skills, check-workflow removes project rules that duplicate the Skills, and review-and-merge and fix-feedback share a Review-round definition and skip Change Requests with repeated back-and-forth. This file is release input and does not itself prove publication. Before installing, confirm that both the remote `v0.2.7` Tag and a non-draft [GitHub Release](https://github.com/philfanzhou/ForgeSteward/releases/tag/v0.2.7) exist. The actual full commit SHA, release PR, and final main-branch CI links are recorded in the Release body.

## Changes since v0.2.6

From [PR #22](https://github.com/philfanzhou/ForgeSteward/pull/22), [PR #24](https://github.com/philfanzhou/ForgeSteward/pull/24), and [PR #23](https://github.com/philfanzhou/ForgeSteward/pull/23).

### Skills are the sole authority for workflow policy

- The four working Skills no longer adopt equivalent workflow rules separately defined by a repository, including readiness gates, task granularity, and Review budgets and rounds. Repository conventions still govern language, title and commit formats, template fields, merge methods, required checks and approvals, branch protection, and build and validation commands.

### prepare-work

- Added feature-level classification: work is feature-level when it involves three or more public protocol surfaces, three or more stateful outputs, or couples multiple areas among transactions and concurrency, data migration, sensitive data flows, and capability activation. If it cannot be reduced to one slice, split it into a tracker and tasks with dependencies; the tracker is not selected. A second independent contract, data migration, or interface group requires a separate Issue.
- Complex protocol or state tasks must provide one semantic model and work through end-to-end outcomes for each scenario. Structural checks are not evidence that the semantics are complete and consistent.
- The readiness gate incorporates Issue constraints previously in project rules and templates: identify the implementation repository and dependencies; cover applicable failure, cancellation, safety, authentication and keys, data migration, concurrency, compatibility, and rollback outcomes in acceptance criteria; for security or robustness tasks, state guarantees, exclusions, caller responsibilities, and supported inputs; include public documentation, configuration, migration history, and deployment paths in the audit; close prerequisites and align platform dependency links and labels with actual state; create and link separate Issues for adjacent existing defects; treat blank template fields as incomplete; add the ready marker only when the gate passes and remove it otherwise.
- Target-repository scheduling rules no longer take precedence over the Skill.

### execute-work

- If implementation reveals feature-level scope that cannot be narrowed, stop that item and split it into tracked work. Check the original Issue's semantic model, and record the end-to-end scenarios actually worked through for designs delivered as documentation.
- Each Change Request closes only one original Issue and records actual commands, results, and reasons for skips in its body.

### review-and-merge and fix-feedback

- Unified round definition: one back-and-forth round occurs when an author pushes new commits in response to Review Feedback requiring changes. Count from the platform timeline and handoff records, taking the larger count if they disagree; a new session does not reset it.
- Change Requests with 3 or more back-and-forth rounds are excluded from the frozen list and await human handling. Review performs no review, merge, or comment; fix performs no modification, push, or thread reply. Output records only the link, round count, and counting evidence. Items explicitly named by the user in the current invocation are exempt.
- For items with 2 completed rounds, audit scope and semantic completeness commit by commit before the third review or repair. Changes that cannot be traced to original acceptance criteria must block progress or be removed and tracked separately.
- review-and-merge treats a linked tracker or a single task that is actually feature-level as an in-scope blocker. Neither Skill adopts repository Review budgets; optional suggestions do not block merging.

### check-workflow

- Replaced standard-block synchronization with deletion only, without adding rules: remove the `forge-steward:workflow` and `forge-steward:claude-rules` blocks written by `0.2.5` and `0.2.6` using `scripts/remove_workflow_blocks.py --check|--write`, plus workflow policies duplicating the Skills in Agent instructions, `CONTRIBUTING.md`, collaboration documents, and Issue/Change Request templates. This applies to both project-authored rules and old additions. See bundled `references/skill-owned-rules.md` for decision criteria.
- Before deletion, check each rule against an equivalent clause in the maintained Skills. Rules without an equivalent meaning are still removed, but must be listed separately as gaps in the Skills in the Change Request, quoting the original text.
- Removed `assets/` templates, `references/legacy-additions.md`, `references/agent-entrypoints.md`, and `scripts/sync_workflow_block.py`. The delivery branch is now `forge-steward/remove-skill-duplicates`.
- See [0.2.7 removing project rules that duplicate Skills](../check-workflow-scenarios.md#027-removing-project-rules-that-duplicate-skills) for decisions, migration notes, and J01–J19 scenarios; see [Skill workflow policy scenarios](../skill-owned-policy-scenarios.md) for the four working Skills.

### Repository maintenance rules

- This repository's `AGENTS.md` adds a rule: when making changes, an Agent automatically bumps the version only when `VERSION` equals a published version; otherwise it retains the unreleased target version. This rule applies only to the ForgeSteward repository and is not distributed with plugins.

## Migration

- **check-workflow (incompatible change to default external writes)**: the first run after upgrading removes old blocks and workflow rules duplicating the Skills from Agent instructions, contribution documents, and templates in one PR/MR, **including rules written by the project itself**. Maintainers can withdraw any deletion during review. After deletion, these constraints apply only when the Skills are invoked; sessions and contributors not using the Skills no longer find them in project documents.
- Projects needing workflow policies different from the Skills can no longer override them through project rules; the Skills themselves must be modified.
- The four working Skills no longer follow repository-defined readiness gates, Review budgets, or task-granularity rules.
- review-and-merge and fix-feedback no longer process Change Requests that have reached 3 back-and-forth rounds. Further progress requires human handling or explicitly naming the item when invoking the Skill.
- This version supersedes open `forge-steward/workflow-block` Change Requests created by `0.2.5` and `0.2.6`; the Skill reports them without automatically closing them. The 0.2.5 G01–G14 and 0.2.6 H01–H10 scenarios no longer apply.

## Installation, upgrade, and rollback

Use these commands only after confirming this version has been released, in a new environment without a marketplace of the same name. For an existing installation, follow the [version switching and cleanup guide](../versioned-installation.md) to record the selected subset, scope, and source; uninstall old copies, replace the marketplace ref, and reinstall the original subset. Do not add the same marketplace twice or edit caches directly. The guide's `v0.2.1` / `find-work` examples are historical; for this version, replace both with `v0.2.7` and the actual plugin names in the table above.

Example for a new Codex environment (install other plugins individually using the table above):

```bash
codex plugin marketplace add philfanzhou/ForgeSteward --ref v0.2.7
codex plugin add check-workflow@forge-steward
codex plugin list
```

Example for a new Claude Code environment:

```text
/plugin marketplace add philfanzhou/ForgeSteward@v0.2.7
/plugin install check-workflow@forge-steward
```

For OpenCode, use a separate snapshot and replace the absolute placeholder paths below. Run installation commands from the target repository you want to maintain:

```bash
git clone --branch v0.2.7 https://github.com/philfanzhou/ForgeSteward.git /absolute/path/ForgeSteward-v0.2.7
git -C /absolute/path/ForgeSteward-v0.2.7 rev-parse HEAD
python3 /absolute/path/ForgeSteward-v0.2.7/scripts/opencode.py install --all --project .
python3 /absolute/path/ForgeSteward-v0.2.7/scripts/opencode.py status --all --project .
```

Before installing, confirm that the checkout SHA matches the Release. For an existing installation, use `update --all --project .` from the same snapshot's installer, or specify the recorded subset and `--user`, instead of repeating `install`. If local customizations trigger protection, back them up and inspect them before deciding what to do; do not force an overwrite.

For ZCode, follow [fixed versions and rollback](../zcode.md#fixed-versions-and-rollback) to add the root of the verified, separate `v0.2.7` checkout as a local marketplace, select the plugin subset, and confirm the installed versions. Before switching, save the original source, uninstall old plugins, and remove the old marketplace. Do not directly reuse Codex's `--ref` or Claude's `@tag` syntax.

Upgrading from `v0.2.6`, `v0.2.5`, `v0.2.4`, or `v0.2.3` does not change installation IDs or invocation methods. From `v0.2.1` or earlier, first remove retired `find-work`, install `prepare-work` instead, and add `execute-work` as needed; there is no old-name alias. Confirm every selected plugin is `0.2.7`. Roll back with the same procedure by selecting the retained `v0.2.6`. Rollback does not restore project rules removed by check-workflow or undo project changes, merges, or hosting-platform operations already performed.

## Validation and exclusions

Before release, run the full unit suite, unified-version, marketplace, resource, and format validation, and relative-link checks. `tests/test_check_workflow_blocks.py` validates the block-removal script in temporary directories. The installer checks on all three operating systems and the pinned OpenCode discovery check must pass for both the PR and final main commit. Record actual results in the PR / Release.

An Agent decides which workflow-policy clauses to remove using the reference document; this is not a deterministic script result. J09–J19, K01–K11, E11–E13, R01–R06, and X01–X03 are manual rule walkthroughs, not independent Agent model-behavior evaluations. PR #22 ran the block-checking script read-only in one real consumer repository and manually prepared its cleanup Change Request under the new rules; it was not yet merged. PR #24 used that cleanup result to fill missing Issue constraints in prepare-work. ZCode remains a development preview; GUI marketplace lifecycle and model behavior are not validated by these checks.

This release distributes only a Git snapshot and GitHub's automatic source archives, with no separate build packages. It does not change real local installations or user configuration.
