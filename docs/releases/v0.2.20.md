# v0.2.20

本文件是 `v0.2.20` 的发布输入。远端同名附注 Tag 和非 draft GitHub Release 都存在，才算发布完成。

这一版让 work-cycle 在运行环境支持时把能同时做的事同时做：多个 Issue 同时实现，多个 PR 同时审查和修复，合并一次一个；同时把默认最大轮数从 5 改为 10。审查标准、合并条件和“每个 PR 最多改 3 次”都没变。

## 改了什么

- **默认最多 10 轮**（[PR #71](https://github.com/philfanzhou/ForgeSteward/pull/71)，[Issue #70](https://github.com/philfanzhou/ForgeSteward/issues/70)）：不指定轮数时最多跑 10 轮；准备阶段没有可做的 Issue 时照样提前结束。
- **准备阶段写清先后关系**（[PR #72](https://github.com/philfanzhou/ForgeSteward/pull/72)，[Issue #66](https://github.com/philfanzhou/ForgeSteward/issues/66)）：每个入选 Issue 写明预计改动范围、和同批其他 Issue 的关系（代码依赖、改动重叠、互不相干）以及验证要用的共享资源。依赖同批另一个 Issue 的可以同批入选，等前置合并后开工。新规则在 prepare-work 的 `references/batch-relations.md`。
- **本地验证防撞车**（[PR #73](https://github.com/philfanzhou/ForgeSteward/pull/73)，[Issue #67](https://github.com/philfanzhou/ForgeSteward/issues/67)）：work-cycle 新增 `scripts/resource_lock.py`，锁放在目标仓库的 git 公共目录，所有 worktree 共用；验证先隔离，隔离不了的按资源排队，重活另有上限；并发时失败的检查先单独重跑，区分撞车和真问题。锁不能用时不并发。规则在 work-cycle 的 `references/verification.md` 和 review-and-merge 的 `references/concurrent.md` 等处。
- **按 Issue 并发实现**（[PR #74](https://github.com/philfanzhou/ForgeSteward/pull/74)，[Issue #68](https://github.com/philfanzhou/ForgeSteward/issues/68)）：子 Agent 合计默认最多 3 个，机器核心少时下调；编排按先后关系决定开工；worktree 放在仓库目录外，有子模块时改用独立 clone；新建 Issue 前在锁内检索，避免重复建单。
- **按 PR 并发审查和修复，合并一次一个**（[PR #75](https://github.com/philfanzhou/ForgeSteward/pull/75)，[Issue #69](https://github.com/philfanzhou/ForgeSteward/issues/69)）：每个 PR 自己走“审查 → 修复 → 再审查”；合并前在锁外用最新主线复核有重叠的改动，进合并锁后确认主线没再变才合并并清理；仓库要求分支最新时同时给其他待合并 PR 派同步。

## 升级需要做什么

技能名、调用方式、安装方式和配置都没变，没有数据迁移。按[固定版本安装、升级与回退](../versioned-installation.md)更新已安装的插件即可；用 work-cycle 时六个插件要升到同一版本。

行为上的变化：
- 不指定轮数时最多跑 10 轮。
- 运行环境支持后台子 Agent 且锁脚本可用时，work-cycle 会同时运行多个子 Agent，在仓库目录外创建 worktree（如 `<仓库上级目录>/<仓库目录名>-forge-steward/`），并在目标仓库的 `.git/forge-steward/locks/` 下保存锁。合并后会清理已合并 PR 自己的 worktree。
- 多个 PR 的 CI 可能同时排队。

## 验证情况

- 本地测试 158 项：152 项通过，6 项因环境不适用而跳过；其中新增锁脚本测试 10 项（含 8 个进程同时取锁、worktree 共用锁）。
- 技能长度检查（含 Windows 换行余量）、版本一致检查（`sync_marketplace.py --check`）、`git diff --check` 通过。
- 各 PR 的三个系统安装器检查和 discovery 检查全部通过。

没验证的：调度与并发规则只做了场景推演，没有在真实仓库里端到端运行；不能保证模型每次都照做。
