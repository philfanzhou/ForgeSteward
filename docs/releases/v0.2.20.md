# v0.2.20

This file is release input for `v0.2.20`. Publication is complete only when both the matching remote annotated Tag and a non-draft GitHub Release exist.

This release let work-cycle perform independent work concurrently when the runtime supports it: multiple Issues in implementation and multiple PRs in review/repair, with one merge at a time. The default maximum cycle count increased from 5 to 10. Review standards, merge conditions, and the three-repair limit per PR remained unchanged.

## Changes

- **Up to 10 cycles by default** ([PR #71](https://github.com/philfanzhou/ForgeSteward/pull/71), [Issue #70](https://github.com/philfanzhou/ForgeSteward/issues/70)): without an explicit count, run at most 10 cycles; still stop early when preparation finds no eligible Issues.
- **Record ordering during preparation** ([PR #72](https://github.com/philfanzhou/ForgeSteward/pull/72), [Issue #66](https://github.com/philfanzhou/ForgeSteward/issues/66)): each selected Issue records expected changes, relationships to the batch's other Issues—code dependency, overlapping changes, or independence—and shared verification resources. An Issue depending on another selected item may join the same batch but starts after its prerequisite merges. Rules are in prepare-work `references/batch-relations.md`.
- **Avoid local verification collisions** ([PR #73](https://github.com/philfanzhou/ForgeSteward/pull/73), [Issue #67](https://github.com/philfanzhou/ForgeSteward/issues/67)): work-cycle adds `scripts/resource_lock.py`, with locks in the target repository's common Git directory shared across worktrees. Isolate verification first, queue resources that cannot be isolated, and separately limit heavy work. Rerun concurrent failures alone to distinguish collisions from defects. Disable concurrency if locks cannot work. Rules include work-cycle `references/verification.md` and review-and-merge `references/concurrent.md`.
- **Concurrent implementation by Issue** ([PR #74](https://github.com/philfanzhou/ForgeSteward/pull/74), [Issue #68](https://github.com/philfanzhou/ForgeSteward/issues/68)): default total maximum 3 subagents, reduced on machines with fewer cores. Orchestrator uses relationships to schedule starts. Keep worktrees outside the repository; use independent clones for submodules. Search under lock before creating Issues to avoid duplicates.
- **Concurrent PR review/repair, one merge at a time** ([PR #75](https://github.com/philfanzhou/ForgeSteward/pull/75), [Issue #69](https://github.com/philfanzhou/ForgeSteward/issues/69)): each PR independently follows review → repair → rereview. Recheck overlapping changes against latest main outside the merge lock, then confirm main has not changed under the lock before merging/cleaning. When up-to-date branches are required, dispatch synchronization for other pending PRs together.

## Upgrade steps

Skill names, invocation, installation, and configuration did not change; no data migration was needed. Update installed plugins using [fixed-version installation, upgrades, and rollback](../versioned-installation.md). All six must use the same version for work-cycle.

Behavioral changes:

- Up to 10 cycles when no count is given.
- With background subagents and a usable lock script, work-cycle runs multiple subagents, creates external worktrees such as `<repository-parent>/<repository-name>-forge-steward/`, and stores locks under the target repository's `.git/forge-steward/locks/`. After merge it cleans that PR's own worktree.
- Multiple PRs' CI may queue concurrently.
