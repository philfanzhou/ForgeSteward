# Prepare Work

## 目标与授权

把原 Issue 推进到下一位执行者只凭 Issue 就能开工的状态。发现候选、技术调查、最小实验、方案收敛和 Issue 整理属于同一准备流程；不要只跑一轮调查就把仍可自主完成的下一步交给用户。不要实施生产改动、创建实现分支或 Change Request，也不要生成或执行实现 prompt。

用户明确调用本技能且未限制范围时，默认包含必要调查和原 Issue 更新；用户要求只读、只讨论或限定写入位置时遵守该边界。隐式匹配技能或在讨论中提及名称不新增授权。依据实际远端选择连接器、CLI 或托管平台 API，不要求特定平台。读取、实验及写入遵守用户授权、实际所属仓库规范和环境权限。

Issue ready 门禁、任务粒度和准备交接以本技能为准，不采用目标仓库另行规定的同类工作流规则；语言、标题格式、Issue 模板结构、平台权限等项目约定仍按所属仓库执行。

## 冻结队列与证据基线

1. 识别目标仓库、默认分支、远端和工作区状态，刷新远端元数据，以最新远端主线提交为审计基线，不覆盖用户改动。读取仓库规范、已有 tracker、主线、上轮遗留和用户的数量限制。
2. 冻结当前开放 Issue 及 Change Request 完整清单，记录时间、基线和顺序。调查期间新发现不自动加入候选；本轮按任务粒度规则从冻结候选拆分出的 task 继承该候选的冻结身份，逐项判定门禁，不属于冻结后新出现的 Issue。没有既定主线时，依据用户目标和仓库优先级，从存量中选定本轮主线，不新造永久排期。
3. 区分存量与周期新增。清理周期基线沿用既有 tracker 或上轮交接记录，不因重跑重置；没有记录时以本轮冻结时间建立基线，按授权写入既有 tracker 的当前调度段落，无可写位置时在过程中说明。周期基线时已开放的 Issue 为存量；从存量拆分出的 task，以及为解除某个存量 task 的真实前置而新建、并已作为其平台依赖关联的 task，继承存量身份。基线之后因审计、Review、CI 或新需求新建的其余 Issue 为周期新增。清理周期继承期初 task、未完成范围和退出条件；新增、返工及父级结项单列，拆分或迁移不冒充存量交付。
4. 核对原 Issue、历史评论、直接前置、父子关系和关联实现；关闭关键字、平台关联、正文、分支及验收范围重合均需检查。已有开放实现转交审查或修复，不重复准备一份实现。关联不明确时查证，不推定不存在。
5. 跨仓任务保留原 Issue 身份，识别实现所属仓库并读取其规则和开放实现；不能因本仓没有代码退回公共库巡检，也不复制同范围任务。
6. 完整阅读将改动的相关成员、测试、公开契约及直接受影响调用路径，按任务检查公开文档、配置、注册、持久化与数据迁移历史、部署路径等边界。已有完整审计时核对基线差异、覆盖范围和未决事项，无相关变化复用证据；相关行为变化补读受影响完整成员及测试，证据缺失则补齐。不因无关提交反复全仓审计，也不把旧绿色结果当作未来实现的验收。

## 持续推进主线阻塞

完成冻结清单的轻量分诊（见「Ready 门禁与分诊」）后，优先处理已领取任务和主线存量任务的准备缺口。主线存在可自主推进的阻塞时，即使已有其他 ready 小项，也先推进主线，不以新找到的数量或一轮调查结束为完成标准。主线行动需要等待长耗时结果（例如 CI、环境构建、外部回复）时，等待期间推进其余候选，结果可用后回到主线；等待不解除主线的持续推进义务，也不把主线判为外部阻塞。主线推进到 ready 或确认真实阻塞后，按批次填充顺序继续准备其余候选以填满本轮批次（见「Ready 门禁与分诊」）；先推进主线不等于只输出主线项。

对每个准备缺口循环执行：

1. 记录具体问题、阻塞类型（真实前置、技术设计、环境、外部决策）、现有证据和解除条件。核对前置是否已关闭，删除过时等待；排期先后不伪装成技术依赖。
2. 选择能改变结论的最小行动：读完整调用链、比较具体方案、运行最小原型或失败实验、验证专项环境路径。每个行动有明确问题和判定标准。实验在隔离的临时环境进行，保留可复现命令、结果与必要产物位置；不提交生产实现，也不触及用户未授权的资源。
3. 根据代码、契约和实验自主完成常规技术选择，将结论落回原 Issue 的范围、方案及验收。实验失败也要说明排除了什么、下一条可执行路径是什么。
4. 重新检查准备缺口。仍有授权范围内的具体行动就继续下一步，直至满足 ready 门禁或证据表明确实依赖外部决定、权限、环境或未交付前置。不得以“已做一个实验”“可以另开 unblock”“请用户继续调查”结束尚可推进的任务。条件未变时也不得重复同一实验空转。

真实外部阻塞须写明已尝试路径、尚缺的具体输入、负责角色、解除证据和恢复动作；需要用户回答时在过程中提出具体问题，同时继续其他独立工作。无可用权限不等于问题已经解除，无法读取必要仓库也不等于没有工作。保存中间证据后继续冻结清单中可推进的项；不以持续造小任务或扩大审计寻找小修复来掩盖主线阻塞、填充批次。

### 存量阻塞复查

存量候选带有阻塞标记或平台依赖关联时，每轮重新核对，不沿用标签或上轮结论跳过：

1. 逐条读取依赖关联的实际状态和已记录的解除条件。前置已全部关闭，或条件已满足（例如维护者已答复、前置已合并、环境已具备）时，按授权移除过时的阻塞标记，按门禁深入准备。
2. 区分技术前置与排期顺序。只有代码、契约、数据或环境上的真实依赖才阻止入选；只表达批次先后、能基于最新主线独立实施的关联，按授权改为非阻塞关联并在原 Issue 记录依据后判定门禁。维护者已写明理由的顺序要求保持不变。
3. 依赖尚在审查的 Change Request 或其他未合并前置时，本轮仍完成审计、方案和验收准备，写明前置合并后需要复核的差异范围；该项本轮不入选，前置合并后只补查差异即可判定。
4. 解除阻塞需要维护者执行具体动作（作出决定、发布前置版本、提供环境或权限）时，在过程中写明该动作、负责角色及可解除的存量 task，同时在原 Issue 记录，不笼统挂起。

## Ready 门禁与分诊

只有同时满足以下条件才入选；门禁以本节为准，Issue 的栏目按所属仓库模板填写。ready 标签等平台标记只反映本门禁的结论：门禁全部满足后才按授权添加，门禁不再满足时按授权移除过时的标记。

- 没有覆盖本次范围的开放 Change Request，已知范围冲突有可执行的处理方式。
- 原 Issue 写清最小范围、排除项、实施方案、实现所属仓库、依赖和可逐条验证的验收。验收覆盖成功结果，以及适用的失败、取消、安全、认证与密钥、数据迁移和并发结果，不适用的写明理由；涉及公开接口、持久化数据或配置时写明兼容与回滚结果。修复须覆盖多条调用路径时，方案写明共同不变量和修复落点。
- 安全或健壮性任务分别写明保证、非保证、调用方责任和适用输入，不为便于收敛而缩减既有保证；其他任务明确写“无”。
- 将改动的实现、测试、公开契约，以及适用的公开文档、配置、数据迁移历史和部署路径已经完整审计，结论有基线和可读取证据；常规设计选择已经收敛，不能只凭描述清楚、已有 ready 标签或历史 CI 结果入选。
- 真实前置均已关闭，平台上的依赖关联和状态标记与实际前置一致；技术设计和必要环境满足实际开工门禁；允许交由 CI 验证的项目须按仓库规则明确可用验证路径，不把未知环境当作已通过。
- 能独立基于最新主线实施，不依赖另一个入选项或未合并 Change Request 的代码。
- 一项 Issue 对应一个可独立验证、可单独提交 Change Request 的切片；包含第二个独立契约、数据迁移或接口组时拆为独立 Issue。同时涉及三个或以上公共协议面、三个或以上有状态产物，或把事务与并发、数据迁移、敏感数据流、能力启用中的多个领域耦合在一起时，按 feature 级处理；不能收敛为单一可独立验证的切片时，拆成 tracker 和有依赖关系的 task。tracker 不入选，也不接收实现 Change Request；拆分出的 task 继承冻结身份并逐项判定门禁，依赖链上仍依赖未合并前置的 task 不入选。所有改动都能追溯到一组宽泛验收，不能证明它是单一 task。
- 复杂协议或状态任务在原 Issue 或其引用的唯一权威位置提供语义模型，至少覆盖：事件 × 产物 × 结果、产物 × 持久化关联、入口 × 外部输入、敏感值 × 信任边界与数据流、实施任务 × 能力启用阶段；并用端到端场景逐一演算成功、失败、取消、安全和并发路径的唯一结果。解释性文字引用该模型，不在多份文档中复制第二套状态规则。链接、表格、语言、构建或测试通过只验证形式，不能证明语义闭合；不适用时写明理由。
- 审计发现的邻近问题已去重分诊并记录归属：破坏本任务验收或既有保证的问题纳入本任务，或作为真实前置处理；其余发现按下文登记规则在原 Issue 链接或记录；确认没有时明确记录“无”。不要求每个邻近发现都新建 Issue 后才能 ready。
- 所属仓库模板要求的栏目均已填写，不适用的栏目写明“无”或“不适用”及理由；栏目留空视为该项准备尚未完成。完整交接已经可从原 Issue 读取，聊天记录、执行 prompt 或编号输出不能代替。

新发现先搜索开放及关闭 Issue/Change Request，有对应项则补证据。登记以不增加 Issue 数量为先：同一缺陷模式或共同不变量（例如多条路径上的同类取消、并发或异常边界缺陷）归并为一个 Issue；已有同类开放 Issue 时追加路径和证据，不另建。只有已确认可复现、独立且没有同类登记的缺陷，才按授权新建一个归并 Issue；可选改进、推测性风险和不影响已声明保证的整洁问题只记录在原 Issue，不新建。ready 已被撤销的 Issue（例如维护者在多轮往返后交回准备阶段），先拆分或重建语义模型再重新判定门禁，不以补充个别条目恢复 ready。已关闭任务的验收遗漏回链原 task、原实现与遗漏条目，作为返工。已接受的非保证没有新证据或范围变化时不反复登记为 bug。登记不自动扩张当前范围或队列，新登记项属于周期新增；需立即处置的严重风险（安全漏洞、数据丢失或损坏、主线构建或 CI 持续阻断）记录实际影响及恢复主线条件。

默认上限为 10 项，用户数量要求优先。批次优先用存量填满，按以下层级逐层准备；前一层候选全部推进到 ready，或已记录不能入选的具体原因之前，不准备下一层（等待长耗时结果时的例外见下文）：

1. 存量 task：主线在前，其后按可解除的存量阻塞数量、依赖和价值排序。
2. 周期新增中需立即处置的严重风险。
3. 其余周期新增：仅当前两层已处理完且批次仍有空位时才准备，并在过程中说明存量未能填满批次的原因。

深入准备前，先用只读查询对完整冻结清单做轻量分诊，并标注每项属于存量还是周期新增：已有开放实现或属于 tracker 的候选，直接判为本轮不能入选并记录原因；周期新增中依赖未合并前置，或已记录真实外部阻塞且解除条件未变的，同样直接排除。存量候选不因阻塞标记或上轮结论在分诊中排除，须按「存量阻塞复查」逐项核对。其余候选标注已知准备缺口。分诊只用于排序和排除确定不能入选的项，不代替门禁判定，不因预估投入大而排除候选。

分诊遇到 tracker、epic、workstream 等父项且其子项已全部关闭时，核对父级验收：验收在最新主线上有证据满足时，按授权关闭并单列为父级结项，不计作交付，也不进入列表；仍有差额时写明剩余范围，差额已有开放 Issue 就链接，没有且属于具体可实施范围时，按授权拆为 task，该 task 继承存量身份。不借结项开展全仓审计。

按批次填充顺序逐项准备。主线项达到 ready 或真实阻塞后，继续推进其余候选，直到入选数达到上限或用户要求的数量，或剩余候选均已判定不能入选并记录各自原因；此前入选数少不是结束理由。缺少审计、验收、邻近问题归属或模板栏目等可在授权范围内补齐的候选须先补齐再判定，不直接排除。非主线候选需要多轮长耗时调查时，保存证据和下一动作后可先推进同层中排在其后的候选，避免少数长耗时调查占满本轮而使接近 ready 的候选未被处理；延后不等于判定不能入选，批次未满时须回到该项继续推进。等待长耗时结果期间可以推进下一层候选，但结果可用后先回到存量；入选数超过上限时优先保留上层项，最终列表按层级和排序输出。不凑数：不降低门禁，不为增加数量拆分本应单一的 Issue 或新建任务，不扩大审计寻找小修复，也不纳入冻结后新出现的 Issue（本轮从冻结候选拆分出的 task，以及为解除存量真实前置而新建的 task 除外）。入选数少于上限时，在工作过程中说明其余候选的未入选原因，最终输出仍只含列表。

输出前复核：入选项的相关主线变化、前置和新开放实现；以及因外部决定、权限、环境或前置未关闭而未入选的冻结候选，其解除条件在本轮已满足（例如用户已在过程中回答、权限已补齐、前置已关闭或合并）时恢复准备并重新判定门禁，入选数仍受上限约束。只补查受影响部分，不把新 Issue 扩进冻结清单。

## 持久化交接与恢复

在原 Issue 更新当前准备结论，沿用既有 tracker 的单一当前调度段落，不叠加相互矛盾的“最新状态”。按需保留：原 Issue 链接、存量或周期新增身份、实现仓库及主线、审计 commit 和覆盖范围、方案与排除项、验收及验证计划、实验命令/结果/产物、邻近问题归属、依赖及冲突、阻塞与恢复条件。在既有 tracker 的当前调度段落按授权更新清理周期计数：周期基线、存量剩余及本轮存量入选数、本轮新建 Issue 数及周期新增入选数、父级结项数，未知计数不推测。历史证据留在评论或编辑历史；实际实现 head、验收结果和 review 轮次尚不存在时写不适用，不虚构通过。

只读模式下，已有完整交接的 Issue 仍可入选；缺少交接且无写入授权时，在过程中说明缺口和所需授权，不能靠最终编号掩盖缺失。写入结果不确定时先回读，避免重复发布；写入失败的必要交接不视为完成。

切换任务或压缩上下文前保存完整冻结清单、已处理/待处理状态、证据位置和下一动作。上下文切换不重置队列，也不把未完成调查判成外部阻塞。只清理本任务拥有且确认可安全删除的临时环境；需要复现的产物先持久化。

## 最终输出契约

最终回复只能是一行有序 Issue 列表，项间使用英文逗号加空格；没有标题、解释、摘要、Markdown 链接、代码块、prompt 或手动换行。同一跟踪仓库且上下文明确时使用 `#123, #145, #167`。跨跟踪仓库时使用平台支持的完整限定标识；无法唯一定位平台或仓库时使用原 Issue 完整 URL，仍在同一行。实现跨仓本身不改变原 Issue 身份，所属仓库写在 Issue 内。

没有符合门禁的项输出 `[]`。此前须已完成可执行的准备行动，并在 Issue 或过程中交代真实阻塞、无权限、空队列或全部完成的事实；不能以 `[]` 代替尚可继续的准备。进度说明和必要问题放在工作过程中，最终不重复。准备完成不等于功能交付，不因 ready 就关闭 task。
