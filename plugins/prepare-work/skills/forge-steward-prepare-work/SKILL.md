# Prepare Work

## 目标与授权

把原 Issue 推进到下一位执行者只凭 Issue 就能开工的状态。发现候选、技术调查、最小实验、方案收敛和 Issue 整理属于同一准备流程；不要只跑一轮调查就把仍可自主完成的下一步交给用户。不要实施生产改动、创建实现分支或 Change Request，也不要生成或执行实现 prompt。

用户明确调用本技能且未限制范围时，默认包含必要调查和原 Issue 更新；用户要求只读、只讨论或限定写入位置时遵守该边界。隐式匹配技能或在讨论中提及名称不新增授权。依据实际远端选择连接器、CLI 或托管平台 API，不要求特定平台。读取、实验及写入遵守用户授权、实际所属仓库规范和环境权限。

Issue ready 门禁、任务粒度和准备交接以本技能为准，不采用目标仓库另行规定的同类工作流规则；语言、标题格式、Issue 模板结构、平台权限等项目约定仍按所属仓库执行。

## 冻结队列与证据基线

1. 识别目标仓库、默认分支、远端和工作区状态，刷新远端元数据，以最新远端主线提交为审计基线，不覆盖用户改动。读取仓库规范、已有 tracker、主线、上轮遗留和用户的数量限制。
2. 冻结当前开放 Issue 及 Change Request 完整清单，记录时间、基线和顺序。调查期间新发现不自动加入候选。清理周期继承期初 task、未完成范围和退出条件；新增、返工及父级结项单列，不因重跑重置基线。没有既定主线时，依据用户目标和仓库优先级选定本轮主线，不新造永久排期。
3. 核对原 Issue、历史评论、直接前置、父子关系和关联实现；关闭关键字、平台关联、正文、分支及验收范围重合均需检查。已有开放实现转交审查或修复，不重复准备一份实现。关联不明确时查证，不推定不存在。
4. 跨仓任务保留原 Issue 身份，识别实现所属仓库并读取其规则和开放实现；不能因本仓没有代码退回公共库巡检，也不复制同范围任务。
5. 完整阅读将改动的相关成员、测试、公开契约及直接受影响调用路径，按任务检查注册、持久化等边界。已有完整审计时核对基线差异、覆盖范围和未决事项，无相关变化复用证据；相关行为变化补读受影响完整成员及测试，证据缺失则补齐。不因无关提交反复全仓审计，也不把旧绿色结果当作未来实现的验收。

## 持续推进主线阻塞

优先处理已领取任务和主线旧任务的准备缺口。主线存在可自主推进的阻塞时，即使已有其他 ready 小项，也先推进主线，不以新找到的数量或一轮调查结束为完成标准。

对每个准备缺口循环执行：

1. 记录具体问题、阻塞类型（真实前置、技术设计、环境、外部决策）、现有证据和解除条件。核对前置是否已关闭，删除过时等待；排期先后不伪装成技术依赖。
2. 选择能改变结论的最小行动：读完整调用链、比较具体方案、运行最小原型或失败实验、验证专项环境路径。每个行动有明确问题和判定标准。实验在隔离的临时环境进行，保留可复现命令、结果与必要产物位置；不提交生产实现，也不触及用户未授权的资源。
3. 根据代码、契约和实验自主完成常规技术选择，将结论落回原 Issue 的范围、方案及验收。实验失败也要说明排除了什么、下一条可执行路径是什么。
4. 重新检查准备缺口。仍有授权范围内的具体行动就继续下一步，直至满足 ready 门禁或证据表明确实依赖外部决定、权限、环境或未交付前置。不得以“已做一个实验”“可以另开 unblock”“请用户继续调查”结束尚可推进的任务。条件未变时也不得重复同一实验空转。

真实外部阻塞须写明已尝试路径、尚缺的具体输入、负责角色、解除证据和恢复动作；需要用户回答时在过程中提出具体问题，同时继续其他独立工作。无可用权限不等于问题已经解除，无法读取必要仓库也不等于没有工作。保存中间证据后继续冻结清单中可推进的项；不以持续造小任务掩盖主线阻塞。

## Ready 门禁与分诊

只有同时满足以下条件才入选；门禁以本节为准，Issue 的栏目按所属仓库模板填写，ready 标签等平台标记只反映本门禁的结论：

- 没有覆盖本次范围的开放 Change Request，已知范围冲突有可执行的处理方式。
- 原 Issue 写清最小范围、排除项、实施方案和可逐条验证的验收；安全及健壮性承诺有明确保证与非保证边界。
- 实现、测试及契约已经审计，结论有基线和可读取证据；常规设计选择已经收敛，不能只凭描述清楚或已有 ready 标签入选。
- 真实前置、技术设计和必要环境均满足实际开工门禁；允许交由 CI 验证的项目须按仓库规则明确可用验证路径，不把未知环境当作已通过。
- 能独立基于最新主线实施，不依赖另一个入选项或未合并 Change Request 的代码。
- 一项 Issue 对应一个可独立验证、可单独提交 Change Request 的切片。同时涉及三个或以上公共协议面、三个或以上有状态产物，或把事务与并发、数据迁移、敏感数据流、能力启用中的多个领域耦合在一起时，按 feature 级处理；不能收敛为单一可独立验证的切片时，拆成 tracker 和有依赖关系的 task。tracker 不入选，也不接收实现 Change Request。所有改动都能追溯到一组宽泛验收，不能证明它是单一 task。
- 复杂协议或状态任务在原 Issue 或其引用的唯一权威位置提供语义模型，至少覆盖：事件 × 产物 × 结果、产物 × 持久化关联、入口 × 外部输入、敏感值 × 信任边界与数据流、实施任务 × 能力启用阶段；并用端到端场景逐一演算成功、失败、取消、安全和并发路径的唯一结果。解释性文字引用该模型，不在多份文档中复制第二套状态规则。链接、表格、语言、构建或测试通过只验证形式，不能证明语义闭合；不适用时写明理由。
- 邻近发现已去重分诊，必要的跟踪归属和链接已持久化；无发现时明确记录“无”。完整交接已经可从原 Issue 读取。

新发现先搜索开放及关闭 Issue/Change Request。有对应项则补证据；只有独立且未登记的问题才按授权创建。被审查或修复阶段撤销 ready 的 Issue，先拆分或重建语义模型再重新判定门禁，不以补充个别条目恢复 ready。已关闭任务的验收遗漏回链原 task、原实现与遗漏条目，作为返工；独立既有缺陷和可选改进分别登记。已接受的非保证没有新证据或范围变化时不反复登记为 bug。登记不自动扩张当前范围或队列；需立即处置的严重风险记录实际影响及恢复主线条件。

默认最多选择 10 项，不凑数；用户数量要求优先。保留用户要求的完整批次，不能找到一项就擅自结束。按主线、有效旧任务、依赖和价值排序。输出前复核入选项的相关主线变化、前置和新开放实现；只补查受影响部分，不把新 Issue 扩进冻结清单。

## 持久化交接与恢复

在原 Issue 更新当前准备结论，沿用既有 tracker 的单一当前调度段落，不叠加相互矛盾的“最新状态”。按需保留：原 Issue 链接、实现仓库及主线、审计 commit 和覆盖范围、方案与排除项、验收及验证计划、实验命令/结果/产物、邻近问题归属、依赖及冲突、阻塞与恢复条件。历史证据留在评论或编辑历史；实际实现 head、验收结果和 review 轮次尚不存在时写不适用，不虚构通过。

只读模式下，已有完整交接的 Issue 仍可入选；缺少交接且无写入授权时，在过程中说明缺口和所需授权，不能靠最终编号掩盖缺失。写入结果不确定时先回读，避免重复发布；写入失败的必要交接不视为完成。

切换任务或压缩上下文前保存完整冻结清单、已处理/待处理状态、证据位置和下一动作。上下文切换不重置队列，也不把未完成调查判成外部阻塞。只清理本任务拥有且确认可安全删除的临时环境；需要复现的产物先持久化。

## 最终输出契约

最终回复只能是一行有序 Issue 列表，项间使用英文逗号加空格；没有标题、解释、摘要、Markdown 链接、代码块、prompt 或手动换行。同一跟踪仓库且上下文明确时使用 `#123, #145, #167`。跨跟踪仓库时使用平台支持的完整限定标识；无法唯一定位平台或仓库时使用原 Issue 完整 URL，仍在同一行。实现跨仓本身不改变原 Issue 身份，所属仓库写在 Issue 内。

没有符合门禁的项输出 `[]`。此前须已完成可执行的准备行动，并在 Issue 或过程中交代真实阻塞、无权限、空队列或全部完成的事实；不能以 `[]` 代替尚可继续的准备。进度说明和必要问题放在工作过程中，最终不重复。准备完成不等于功能交付，不因 ready 就关闭 task。
