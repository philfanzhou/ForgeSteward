## Persist handoff and recovery

Update current preparation conclusions on the original Issue. Use the existing tracker's single current scheduling section; do not accumulate contradictory “latest” states. Retain as needed: original link; backlog/cycle-addition identity; implementation repository/mainline; audit commit/coverage; plan/exclusions; acceptance/verification plan; expected changes, batch relationships, shared resources; experiment commands/results/output locations; adjacent-finding ownership; dependencies/conflicts; blockers/recovery conditions. In the existing scheduling section, update authorized cycle counts: baseline, backlog remaining/selected this round, newly created Issues/cycle additions selected, and parent closures. Do not guess unknown counts. Use everyday phrases such as “tasks already open before this cleanup,” “tasks created during this cleanup,” and “closed parent tasks,” rather than internal category names. “This cleanup” starts at the tracker/handoff baseline and persists across runs, not this invocation's start. Keep historical evidence in comments/edit history. Mark implementation head, acceptance results, and review rounds not applicable when not yet present; never invent passes.

In read-only mode, Issues with complete handoffs may still be selected. If missing handoff cannot be written, explain the gap and needed authorization during progress; a final number cannot conceal it. Read back ambiguous writes before retrying. A failed required handoff is incomplete.

Before switching tasks or compacting context, save the complete frozen list, handled/pending status, evidence locations, and next actions. Context changes neither reset the queue nor make unfinished investigation an external blocker. Clean only task-owned temporary environments confirmed safe to delete, first persisting outputs needed for reproduction.
