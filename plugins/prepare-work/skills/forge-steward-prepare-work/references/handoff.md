## Persist handoff and recovery

Update current preparation conclusions on the original Issue. For one current-state record, use a writable existing tracker or repository-designated location; otherwise use the original Issue handoff. Update its single current scheduling section; do not accumulate contradictory “latest” states, and never invent a tracker. If no writable location exists, state during progress that persistence is unavailable rather than claiming a record. Retain as needed: original link; backlog/cycle-addition identity; implementation repository/mainline; audit commit/coverage; plan/exclusions and settled user decisions; acceptance/verification plan with each blocking criterion's exact source and evidence under [Acceptance sources](readiness.md#acceptance-sources), optional suggestions kept separate; expected changes, batch relationships, shared resources; experiment commands/results/output locations; adjacent-finding ownership; dependencies/conflicts; blockers/recovery conditions. In that scheduling section, update authorized cycle counts: baseline, backlog remaining/selected this round, newly created Issues/cycle additions selected, and parent closures. Do not guess unknown counts. Use everyday phrases such as “tasks already open before this cleanup,” “tasks created during this cleanup,” and “closed parent tasks,” rather than internal category names. “This cleanup” starts at the tracker/handoff baseline and persists across runs, not this invocation's start. Keep historical evidence in comments/edit history. Mark implementation head, acceptance results, and review rounds not applicable when not yet present; never invent passes.

In read-only mode, Issues with complete handoffs may still be selected. If missing handoff cannot be written, explain the gap and needed authorization during progress; a final number cannot conceal it. Read back ambiguous writes before retrying. A failed required handoff is incomplete.

**Pre-publication secret scan.** Before publishing experiment evidence or command output to an Issue or comment, inspect it for secrets. When the repository defines a secret-scan command, run it and record the exact command, result, and coverage, including evidence not scanned. On a hit, a failed or unavailable defined command, or coverage that does not include the complete evidence, redact the value, report what was and was not scanned instead of publishing, and do not claim a pass. If no command is defined, record that absence and the completed inspection; do not claim an automated scan passed. The scan is not authoritative over semantic acceptance and adds no dependency or credential.

When scope is corrected, replace the original Issue's single current handoff, retaining history and still-valid audits, commits, check results, and review counts. Remove invented blockers, identify affected evidence, and refresh only changed facts before resuming; create no duplicate Issue/Change Request and do not reset review counts. Retain real unresolved source conflicts, decision owners, and release evidence. Respect recorded Issue ownership when updating the handoff.

Before switching tasks or compacting context, save the complete frozen list, handled/pending status, acceptance sources, evidence locations, and next actions. Preserve the same record on an explicit stop. Context changes neither reset the queue nor make unfinished investigation an external blocker. Clean only task-owned temporary environments confirmed safe to delete, first persisting outputs needed for reproduction.
