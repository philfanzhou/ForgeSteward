## Ready 门禁与分诊

只有同时满足以下条件才入选；门禁以本节为准，Issue 的栏目按所属仓库模板填写。ready 标签等平台标记只反映本门禁的结论：门禁全部满足后才按授权添加，门禁不再满足时按授权移除过时的标记。

- 没有覆盖本次范围的开放 Change Request，已知范围冲突有可执行的处理方式。
- 原 Issue 写清最小范围、排除项、实施方案、实现所属仓库、依赖和可逐条验证的验收。验收覆盖成功结果，以及适用的失败、取消、安全、认证与密钥、数据迁移和并发结果，不适用的写明理由；涉及公开接口、持久化数据或配置时写明兼容与回滚结果。修复须覆盖多条调用路径时，方案写明共同不变量和修复落点。
- 安全或健壮性任务分别写明保证、非保证、调用方责任和适用输入，不为便于收敛而缩减既有保证；其他任务明确写“无”。
- 将改动的实现、测试、公开契约，以及适用的公开文档、配置、数据迁移历史和部署路径已经完整审计，结论有基线和可读取证据；常规设计选择已经收敛，不能只凭描述清楚、已有 ready 标签或历史 CI 结果入选。
- 真实前置均已关闭，平台上的依赖关联和状态标记与实际前置一致；技术设计和必要环境满足实际开工门禁；允许交由 CI 验证的项目须按仓库规则明确可用验证路径，不把未知环境当作已通过。
- 能独立基于最新主线实施，不依赖另一个入选项或未合并 Change Request 的代码。
- 一项 Issue 对应一个可独立验证、可单独提交 Change Request 的切片；包含第二个独立契约、数据迁移或接口组时拆为独立 Issue。同时涉及三个或以上公共协议面、三个或以上有状态产物，或把事务与并发、数据迁移、敏感数据流、能力启用中的多个领域耦合在一起时，按 feature 级处理；不能收敛为单一可独立验证的切片时，拆成 tracker 和有依赖关系的 task。tracker 不入选，也不接收实现 Change Request；拆分出的 task 继承冻结身份并逐项判定门禁，依赖链上仍依赖未合并前置的 task 不入选。所有改动都能追溯到一组宽泛验收，不能证明它是单一 task。
- 复杂协议或状态任务在原 Issue 或其引用的唯一权威位置提供语义模型，至少覆盖：事件 × 产物 × 结果、产物 × 持久化关联、入口 × 外部输入、敏感值 × 信任边界与数据流、实施任务 × 能力启用阶段；并用端到端场景逐一演算成功、失败、取消、安全和并发路径的唯一结果。解释性文字引用该模型，不在多份文档中复制第二套状态规则。链接、表格、语言、构建或测试通过只验证形式，不能证明语义闭合；不适用时写明理由。
- 审计发现的邻近问题已去重分诊并记录归属：破坏本任务验收或既有保证的问题纳入本任务，或作为真实前置处理；其余发现按下文登记规则在原 Issue 链接或记录；确认没有时明确记录“无”。不要求每个邻近发现都新建 Issue 后才能 ready。
- 所属仓库模板要求的栏目均已填写，不适用的栏目写明“无”或“不适用”及理由；栏目留空视为该项准备尚未完成。完整交接已经可从原 Issue 读取，聊天记录、执行 prompt 或编号输出不能代替。

新发现先搜索开放及关闭 Issue/Change Request，有对应项则补证据。登记以不增加 Issue 数量为先：同一缺陷模式或共同不变量（例如多条路径上的同类取消、并发或异常边界缺陷）归并为一个 Issue；已有同类开放 Issue 时追加路径和证据，不另建。只有已确认可复现、独立且没有同类登记的缺陷，才按授权新建一个归并 Issue；可选改进、推测性风险和不影响已声明保证的整洁问题只记录在原 Issue，不新建。ready 已被撤销的 Issue（例如维护者在多轮往返后交回准备阶段），先拆分或重建语义模型再重新判定门禁，不以补充个别条目恢复 ready。已关闭任务的验收遗漏回链原 task、原实现与遗漏条目，作为返工。已接受的非保证没有新证据或范围变化时不反复登记为 bug。登记不自动扩张当前范围或队列，新登记项属于周期新增；需立即处置的严重风险（安全漏洞、数据丢失或损坏、主线构建或 CI 持续阻断）记录实际影响及恢复主线条件。
