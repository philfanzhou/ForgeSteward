# 旧版增补识别与删除

## 背景

`0.2.4` 及更早的 check-workflow 按“工作流最低约束”逐项判断项目规则，把缺失条款直接写成项目规则的一部分：优先追加到已有的权威工作流文档；没有合适位置时新建一份工作流文档，并在 Agent 入口增加读取指示。这些内容没有标记，提交信息和 Change Request 标题也不固定。

标准区块声明区块外的项目规则优先。旧增补若继续留在区块外，会重复标准区块，或以旧条款覆盖它。因此本技能删除能够确认的旧增补，但不删除项目自行编写的规则。

## 候选位置

只在旧版本可能写入的位置查找：

- 根目录及子目录的 `AGENTS.md`、`CLAUDE.md`；`AGENTS.override.md` 只报告，不修改。
- `CONTRIBUTING.md`、`docs/` 等处的工作流、协作、交付或 Agent 指令文档。
- Issue 与 Change Request 模板。

旧版本不修改非文档配置，所以不在 `opencode.json` 等配置、业务代码、测试或 CI 中查找。标准区块和读取指示区块内部不属于候选。

## 确认删除的条件

一项内容须同时满足以下两类证据，才能确认删除。

**内容特征**，须全部满足：

- 主题属于旧版工作流最低约束的维度：规则来源与阶段应用、准备与实施边界、准备成果与开工交接、任务范围与实施归属、逐条验收、保证与非保证、开工门槛、主线与批次、清单实施与批次结束、Review 分类与结束、修复与复审、新发现分诊、持续交接与证据复用、交付与结项、清理周期、授权与临时环境。
- 以补充形式出现：标题或引言标明“补充”“增补”，或写有旧版要求加入的限定语，例如声明落实而不改变既有政策、不要求历史 Issue 批量重写、不把工作流接入检查设为每次任务的前置步骤；或整份文档、读取指示只为承载或引用这类补充而存在。

**来源证据**：`git log -S`、`git log -L` 或 `git blame` 显示该内容由一次只修改工作流相关文档的提交整段加入，并且该提交、其 Change Request 或关联 Issue 说明这是工作流接入、工作流约束补充或增补，例如提到 check-workflow、ForgeSteward 技能名、工作流接入检查、约束映射或“重跑不重复增补”。

只有内容特征而没有来源证据，或只有来源证据而内容不是补充形式时，列为待维护者决定。

## 不删除的情形

- 项目或维护者自行编写的规则，即使主题相同、措辞相近，或与标准区块要求不同。
- 加入后被其他提交实质修改的内容（空白和换行调整除外）：维护者可能已把它采纳为项目规则，列为待决定。
- 仍被项目自身规则、文档或链接引用的内容，除非引用方本身也是同一批旧增补。
- 维护者已在此前的 Change Request 审查或讨论中明确保留的内容；后续运行只在汇报中注明，不再删除。
- 无法取得完整历史或证据互相矛盾的内容。
- 决策记录、变更日志、发布说明等对旧流程的历史描述。

## 删除方式

- 整段删除确认的增补：从其标题或首行到下一个同级或更高级标题之前，连同因此多出的空行。增补只占章节一部分时，只删除增补的行。不改写、合并或重新排版相邻内容。
- 为旧增补新建、且全部内容都是旧增补的文档整份删除，并删除入口中只指向它的读取指示行。
- 同一次旧增补分布在多个文件时，确认的部分一并删除。
- 同时删除指向被删章节或文档的目录项和链接；引用方属于项目自身规则时，撤回该项删除并列为待决定。
- 不把旧增补中的项目特有内容搬进标准区块，也不代写替代条款。维护者需要保留其中的差异时，在区块外自行编写。

## 记录与重复运行

每项记录：文件、删除前行范围、标题或首行、加入提交与 Change Request、内容特征、来源证据、处理结果（已删除，或待决定及原因）。待决定项在 Change Request 中逐项列出，不自动删除。

删除合入主线后，重复运行不会再发现这些内容；待决定项没有变化时只再次报告，不产生差异。维护者在审查中撤回某项删除时，按上文“明确保留”处理。
