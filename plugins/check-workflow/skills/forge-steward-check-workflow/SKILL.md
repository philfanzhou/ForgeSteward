# Check Workflow

## 目标与授权

帮助代码库接入任务准备、按清单实施、审查交付和修复意见的工作流。用户明确调用本技能（包括仅选择技能、不附加 prompt），或要求执行完整工作流接入时，默认任务是：检查 → 补齐无冲突的缺失约束与必要入口 → 验证 → commit、push 并创建 Change Request（PR/MR），禁止合并。不把“发现缺失”或“本地已修改”当作完整任务的终点，也不要求用户再次补写“请实现并提 PR”。

用户本轮的明确限制优先：仅检查/分析时只报告、不写文件；仅本地修改、不提交或不发布时在相应边界停止。自动选中本技能、引用技能名称或询问其用法，不构成外部发布授权；这类调用只按用户实际请求执行，发布前缺少授权才确认。沿用当前任务中已有效的授权，同时遵守目标仓库权限、审批及交付规则，不能以默认流程绕过限制。

只修改目标仓库内相关工作流约束文档及必要的 Agent 文档入口。保留项目已有规则的文字、含义、适用范围、优先级和加载路径；不能借“接入工作流”替换、弱化或强化已有要求，也不能以新增段落间接覆盖旧规则。遵循目标仓库的文档语言，不把 ForgeSteward 自身的语言、技术栈或工程规则带入使用方。

“补齐实现”只指本技能负责的工作流约束文档及入口，不修改业务代码、依赖、测试实现、CI、分支保护、全局 Agent 配置或权限；不安装插件，不批量整理 Issue，不自动运行其他 Skill，不合并 Change Request。需要额外权限、仓库不允许发布或用户限制发布时，完成允许的本地部分，记录具体阻塞和恢复步骤，不擅自创建远端仓库或改变权限。

## 读取与建立约束映射

1. 定位用户指定的目标仓库、主线和工作区，记录操作模式、基线与已有改动。默认交付模式下，检查主线及是否已有覆盖相同缺口的开放 Change Request；无可复用的本任务分支时，基于最新主线创建独立工作分支。不覆盖用户改动、不夹带其他任务或未合并实现、不在主干直接 commit 或 push；只读模式不创建分支。目标跨仓时分别确认范围，不因接入一个仓库自动修改另一个。
2. 完整读取适用的项目/目录级 Agent 指令、贡献指南、工作流说明和 Issue/Change Request 模板，并沿其声明的引用定位真实规则源。读取已配置的 Agent 文档入口及加载配置，识别覆盖、回退、导入关系；无法读取的来源记为未知。只按需查看验证命令或目录边界的证据，不转为代码缺陷审计。
3. 按 [工作流最低约束](references/workflow-requirements.md) 逐项建立“要求 → 现有来源及适用范围 → 状态 → 缺少部分 → 拟增补位置”。按语义判断，接受等价措辞和现有文件布局，不以固定标题、文件名或模板格式作为通过条件。
4. 状态区分：**已满足**、**缺失且可增补**、**与既有规则冲突**、**不适用**、**来源/语义待确认**。已有更严格或不同但明确的政策原样保留；不能简单取“更严格者”，也不能宣布本 Skill 或新文档优先于项目规则。

重点核对准备与实施之间的交接：准备结论能否从原 Issue 独立恢复，执行是否只处理明确清单，阶段完成与功能交付是否区分。准备、执行、审查和修复是独立入口，不要求安装全部技能、先运行准备技能或自动串联调用；具体输出格式留在各技能中，不复制整套技能正文到项目规则。

## 只增补缺失项

- 对已满足项只引用原文位置，不重复抄写。对部分满足项仅补缺少的语义，不重写原段落、不统一格式、不顺手翻译或迁移旧文档。
- 对可增补项写出具体、有限且可验证的执行条件，并引用项目原有测试入口、术语、任务层级及交付流程。不虚构命令、审批人数、三轮预算、十项批次或“一 PR 一 task”等项目政策；已有这些要求则保留，用户本轮明确的批次要求也不能被默认值缩减。
- 对冲突或未知项，保留原规则，记录来源、触发场景、受影响阶段和需要的具体决定；不写入冲突条款，不扩大成全面规范整改。继续其他独立、无冲突的增补；存在未决必需项时只能报告部分接入，不能声称全部兼容。
- 对仍要求旧 find-work 生成执行 prompt、仅依赖聊天交接或将准备与生产实现绑定的规则，核对实际语义；确与新阶段边界冲突时报告迁移决定，不自动替换旧规则。旧名称仅作为历史记录或示例时不算缺口。
- 优先在现有权威工作流文档中增加缺失段落。确实没有合适位置时才新增一份符合项目布局的工作流文档，并在适用入口增加明确的读取指示。已有“唯一规则源”约定必须保留，不新增第二个权威。
- 增补内容限定用于本工作流，声明其补充性质及原规则来源；不要求历史 Issue 批量套模板、不把接入检查变成每次任务执行的前置审计。具体任务仍须按项目规则验收，规则文档齐全不代表任务 ready。
- 再次运行先检查等价内容及入口。已补齐且来源未变时不产生新段落、时间戳、重复引用或无意义 commit。以前生成的内容一旦成为项目现有规则，也不得自动覆盖或升级；发生冲突时按同一流程报告。

## 多 Agent 入口

读取 [Agent 入口适配](references/agent-entrypoints.md)，只为用户指定或仓库已采用的 Agent 添加必要文档入口；未指定且无现有入口时采用其中的最小通用布局。技能本体保持标准 `SKILL.md` 与相对引用，不依赖特定工具名、shell、平台 API、上下文压缩命令或其他 Skill 已安装。

新增入口前必须验证它不会遮蔽已有回退文件、绕过目录规则或形成循环。复用项目原来的规则源，用薄入口引用，不能给每个 Agent 复制一套工作流正文。需要修改非文档配置、用户级配置或无法验证加载语义时，只报告该适配缺口和可执行下一步，不擅自修改，也不将其算作已兼容。

## 验证与结束条件

1. 对照执行前的文件内容核对 diff：原有文字、模板字段和用户改动均保留；新增内容确实只对应缺失项，没有冲突的隐式重定义。仅有新增行不足以证明语义不变，还须检查规则作用域和加载优先级。
2. 检查每项增补的来源、适用阶段和停止条件；核对准备交接与执行入口的规则是否相容，不把本次规则检查当作具体任务的 ready 审核。检查相对路径存在、入口可达、无导入循环、无同义重复，包含实际使用的根目录和相关子目录。已有检查工具适用时运行；不为验证文档而触发生产流程或安装新工具。
3. 复核约束映射并做一次不写入的重跑判断：每个已完成项应为“已有覆盖”，拟新增差异应为空。缺少来源或保留冲突不靠标记“完成”消除。
4. 已全部满足时以零修改结束，不创建空 commit 或空 Change Request。存在有效增补时，默认交付模式继续下节提交，不在报告或本地 diff 处结束；受限模式在用户指定边界交付。有冲突或环境限制时保留独立已完成部分、具体缺口及下一步，不为追求“完美规则”扩大调查。

## 提交与交接

1. 默认交付模式下，验证通过后只暂存本任务的文档变更，按目标仓库规范 commit、push 到确认的交付分支，并创建指向该仓主线的 Change Request；已有覆盖相同工作的本任务 Change Request 时更新原项，不重复开 PR/MR。其他任务的开放实现只报告覆盖关系，不擅自接管。
2. Change Request 正文列出补齐项及原规则来源、修改范围、验证证据、已接受边界、未解决冲突或适配缺口。独立增补可交付但尚未全部接通时，按项目规则标明部分完成或 draft，不声称完整接入。
3. 创建或推送响应不明确时，先查询远端分支提交和同源 Change Request，确认是否已成功再重试。权限、认证、网络或仓库门禁确实阻止继续时，保存本地提交/差异及准确下一步，区分未提交、已提交未推送、已推送未建 PR/MR；不以准备好的标题正文冒充已创建。
4. 回读实际 Change Request 的链接、base/head 与状态，确认远端包含本次提交后结束；不等待合并、不自行 review-and-merge。只安全清理本任务的临时环境，未交付或仍用于开放 PR/MR 的分支保留。

用目标项目约定的语言汇报：基线与操作模式、约束映射和来源、实际修改文件、原规则保留证据、Agent 入口与验证层级、重跑判断、提交及 PR/MR 链接、未完成差额和下一步。区分“文档及路径已验证”“Agent 实际加载已验证”和“行为已验证”；没有运行目标 Agent 时不得宣称运行时兼容。正常默认流程以已创建/更新 PR/MR 交接，不以已提交冒充已合并。
