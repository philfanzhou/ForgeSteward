# Find Work

## 目标与边界

从当前仓库中筛选真正可以立即实施的 Issue，并生成后续批量执行 prompt。本轮只进行分析、必要调查、Issue 整理和 prompt 生成；不要实现所选 Issue，不要创建实现分支或 Change Request，也不要执行生成的 prompt。

使用当前环境可用的连接器、CLI 或托管平台 API。先从远端信息识别实际平台，不要求 GitHub，也不要把 `gh`、Pull Request 等单一平台工具或术语当作前提。所有读取和写入都必须遵守当前仓库规范及用户授权；若没有写入 Issue 的授权，只输出建议更新内容，不代替用户发布。

## 建立基线并冻结清单

1. 定位仓库根目录、远端、托管平台、默认分支和当前工作区状态。以默认分支的最新远端提交为判断基线；仓库明确以 `main` 为主线时使用最新 `main`。刷新远端元数据时不得覆盖或清理用户改动。
2. 记录基线提交、调查时间和开放 Issue 完整列表；同时冻结当时开放的 Change Request 列表。调查期间新出现的条目不自动加入本轮候选。
3. 将 Change Request 与 Issue 关联。关闭关键字、平台关联、正文引用、分支命名或验收范围明显重合，均可构成“已有开放实现”的证据；证据不足时标为不确定，不要武断认定未关联。
4. 按需检查相关代码、测试、契约、设计记录、里程碑、父子任务、历史评论和开放分支。调查深度以判断范围、验收、依赖和冲突所需为限，不扩大为全仓审计。

## 筛选和排序

一个 Issue 只有同时满足以下条件才算 ready：

- 没有已经覆盖其实现范围的开放 Change Request。
- 范围边界明确，能够说明要改什么以及明确不改什么。
- 验收条件可逐条验证；没有验收条件时，仓库内存在足够明确的等价契约或测试依据。
- 外部依赖、父任务前置条件和环境条件已经满足。
- 能够单独基于冻结时的最新主线实施，不依赖任何未合并 Change Request，也不需要叠加另一个候选项的代码。
- 与相关开放分支没有无法规划的范围重叠。

最多选择 10 个，不要求凑满。执行顺序优先考虑仓库已标识的主线、里程碑或父任务顺序，其次考虑长期未推进但仍有效的旧任务、依赖拓扑和交付价值。不能只按创建时间把废弃或非主线旧 Issue 提前。

对每个入选项说明已知冲突以及实施时的处理方式。只能说明已知风险和缓解方案，不承诺零合并风险。

新发现的问题先检索开放与已关闭条目去重，再按仓库规则登记或提出分诊建议。除非它阻塞当前验收或构成需要立即处理的严重风险，不得自动加入本轮队列，也不得通过持续创建小修复填满批次。

## 没有 ready 项时

复核冻结时的完整开放 Issue 列表，返回零个入选项。选择一个仍属于主线的旧任务，推进其一个具体的设计结论、最小实验或环境阻塞调查；必要且已获授权时更新原 Issue。不要扩大审计，不要另开无关小修复。

随后生成一个只针对该旧任务具体阻塞的执行 prompt。它必须写明已确认事实、待解决阻塞、可执行下一步和停止条件，不能把未满足条件的任务包装成 ready。

## 输出

使用中文输出：

1. 冻结基线：托管平台、仓库、主线提交、调查时间，以及开放 Issue 和开放 Change Request 数量。
2. 实际入选项：按执行顺序列出 Issue 编号、一句话概要、链接、入选依据、已知冲突及处理方式。
3. 排除与分诊摘要：说明主要排除原因、新发现的去重和登记结果；无需逐项复述所有无关细节。
4. 全部入选编号：单独给出有序编号列表。
5. 执行 prompt：将全部实际编号替换进下面文本并原样输出；一个也不要擅自增加。

```text
连续处理 issue #xx、#xx、#xx。逐项读取仓库规范、关联 issue 和历史记录，基于最新 main 完成原范围内的实现及逐条验收，每项提交并推送独立 PR，禁止合并。记录进度、验收和待办后，压缩上下文、安全清理本任务环境，再继续下一项，不在提交一个 PR 后停止，不叠加未合并代码。遇到阻塞先尝试解决，确实无法继续则记录具体原因及下一步，继续其余任务，直到清单全部处理完；不擅自扩充清单。最后中文汇总每项实现、验证、PR 链接及遗留问题，区分已提交与已合并交付。
```

为适配不同平台，最终生成时可以把 `PR` 替换为该平台的 Change Request 名称，把 `main` 替换为仓库明确的默认主线名称；除此之外不要改变执行约束。零项时不要输出带空编号的模板，改为输出前述阻塞推进 prompt。
