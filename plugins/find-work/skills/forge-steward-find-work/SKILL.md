# Find Work

## 目标与边界

从当前仓库中筛选真正可以立即实施的 Issue，并生成后续批量执行 prompt。本轮只进行分析、必要调查、Issue 整理和 prompt 生成；不要实现所选 Issue，不要创建实现分支或 Change Request，也不要执行生成的 prompt。

使用当前环境可用的连接器、CLI 或托管平台 API。先从远端信息识别实际平台，不要求 GitHub，也不要把 `gh`、Pull Request 等单一平台工具或术语当作前提。所有读取和写入都必须遵守当前仓库规范及用户授权；若没有写入 Issue 的授权，只输出建议更新内容，不代替用户发布。

## 建立基线并冻结清单

1. 定位仓库根目录、远端、托管平台、默认分支和当前工作区状态。以默认分支的最新远端提交为判断基线；仓库明确以 `main` 为主线时使用最新 `main`。刷新远端元数据时不得覆盖或清理用户改动。
2. 读取既有主线和上轮遗留，记录基线提交、调查时间和开放 Issue 完整列表；同时冻结当时开放的 Change Request 列表。调查期间新出现的条目不自动加入本轮候选。清理周期另保留期初 task 清单、未完成范围和退出条件，不随每轮调用重置；新增项、返工及父级结项单列，拆分或迁移跟踪位置不算原任务交付。没有既定主线时，依据用户目标及仓库优先级说明本轮选择，不擅自创建永久排期。
3. 将 Change Request 与 Issue 关联。关闭关键字、平台关联、正文引用、分支命名或验收范围明显重合，均可构成“已有开放实现”的证据；证据不足时标为不确定，不要武断认定未关联。跨仓任务须识别代码所属仓库、读取其规范并检查其开放实现，保留原 Issue 的完整链接，不复制同范围任务。
4. 按需检查相关代码、测试、契约、设计记录、里程碑、父子任务、历史评论和开放分支。已有开工审计须核对其基线、覆盖范围和未决事项；无相关变化就复用，相关变化才补查受影响的完整成员、测试和契约。缺少证据时完成必要调查，不用无关主线提交触发重复审计；旧验证不代替修改后的验收。

## 先推进主线阻塞

在筛选 ready 项前检查主线未完成项。已有开放实现的项保持在审查或修复阶段，不另开实现；在本轮权限外的动作记录交接。主线尚无开放实现且受阻时，即使其他小任务 ready，也应在授权范围内推进一个有明确问题、产物和停止条件的设计决定、最小实验或环境调查，不扩大为全仓审计。

记录阻塞类型、证据、下一步、负责角色和解除条件。常规技术选择依据代码和契约完成；确实等待外部决策、权限或环境时，写明具体请求，没有条件变化就不重复同一调查。同一阻塞再次出现且没有新证据时，执行尚未完成的下一步或交接具体外部决定，不能只改写“仍被阻塞”。需立即处置的严重风险可以调整顺序，但须记录实际影响和恢复主线的条件。

调查解除阻塞后，当轮重新检查 ready 条件，允许原冻结列表中的该项入选；调查完成不等于实现完成。主线仍受阻时，如实保留阻塞，其他独立 ready 项仍可入选，不擅自缩减用户要求的批次。

## 筛选和排序

一个 Issue 只有同时满足以下条件才算 ready：

- 没有已经覆盖其实现范围的开放 Change Request。
- 范围边界明确，能够说明要改什么以及明确不改什么。
- 验收条件可逐条验证；没有验收条件时，仓库内存在足够明确的等价契约或测试依据。
- 外部依赖、父任务前置条件和环境条件已经满足。
- 能够单独基于冻结时的最新主线实施，不依赖任何未合并 Change Request，也不需要叠加另一个候选项的代码。
- 与相关开放分支没有无法规划的范围重叠。

最多选择 10 个，不要求凑满。执行顺序优先考虑仓库已标识的主线、里程碑或父任务顺序，其次考虑长期未推进但仍有效的旧任务、依赖拓扑和交付价值。不能只按创建时间把废弃或非主线旧 Issue 提前。

对每个入选项说明已知冲突以及实施时的处理方式。只能说明已知风险和缓解方案，不承诺零合并风险。

新发现的问题先检索开放与已关闭条目去重，再按仓库规则登记或提出分诊建议。当前验收遗漏留在当前任务闭环；已关闭任务的验收遗漏回链原任务、Change Request 和遗漏条目，记为返工；独立既有缺陷与可选改进分别分诊。已接受的非保证没有新证据或范围变化时不反复登记为 bug。登记不自动加入本轮队列；严重风险须明确处置及恢复主线条件，不得通过持续创建小修复填满批次。

## 没有 ready 项时

完成上述主线调查后，复核冻结列表的排除依据。仍没有 ready 项才返回零项，不重复已经完成且条件未变的调查，也不另开无关小修复。

存在可执行调查时，生成仅针对其具体阻塞的 prompt，写明事实、下一步及停止条件；只剩外部等待时输出具体交接请求和恢复条件，不生成无动作的循环 prompt。全部工作已完成或没有有效主线任务时说明事实，不虚构阻塞，不把未满足条件的任务包装成 ready。

## 交接记录

沿用已有 tracker、任务或仓库指定记录位置，保留一份当前状态；仅在授权范围内写入，没有可写位置时在输出中提供可直接交接的完整记录，不自行创建 tracker。字段按实际填写：清理周期基线与主线；task/Change Request 完整链接、实现仓库及主线；审计基线、覆盖范围与证据位置；当前 head、逐条验收证据；意见分类、Review 轮次、已解决意见与已接受边界；阻塞、下一步及解除条件。缺失项标明未知或不适用，不推定验收通过或将轮次归零。

## 输出

使用中文输出：

1. 冻结基线：托管平台、仓库、主线提交、调查时间、开放 Issue 和 Change Request 数量；清理周期的期初 task 完成及剩余、新增项、返工、父级结项和本轮解除的阻塞分别报告，未知计数不推测。
2. 实际入选项：按执行顺序列出 Issue 编号、一句话概要、链接、入选依据、已知冲突及处理方式。
3. 排除与分诊摘要：说明主要排除原因、新发现的去重和登记结果；无需逐项复述所有无关细节。
4. 全部入选编号：单独给出有序编号列表。
5. 执行 prompt：包含全部实际入选项及必要交接信息，使用完整 Issue 链接，逐项注明实现仓库、主线及审计记录位置；没有记录时明确需要补查。下面是执行约束模板，可补充任务上下文和替换平台术语，不擅自增减清单或放宽约束。

```text
连续处理以下全部任务：<按序填写完整 Issue 链接、实现仓库、主线和审计/交接记录>。逐项读取所属仓库规范、原 issue 和历史记录，核对最新主线、依赖及已有开放实现；已有 PR 的不重复创建。复用仍有效的审计并补查相关变化，独立基于所属仓库最新主线完成原范围内实现和逐条验收，每项提交并推送独立 PR，跨仓时回链原 issue，禁止合并，不叠加未合并代码。新发现去重分诊，不自动扩大范围。切换或压缩上下文前，沿用已授权记录位置保存 task/PR、仓库、提交、验收证据、意见分类、review 轮次、已解决意见、已接受边界、阻塞与下一步；没有可写位置时输出完整交接记录。仅清理本任务拥有且确认可安全删除的临时环境，再继续下一项，不在提交一个 PR 后停止。遇到阻塞推进一个具体解决动作；确实无法继续则记录原因及解除条件，继续其余任务，直到清单全部处理完，不擅自扩充清单。最后中文汇总每项实现、验证、PR 链接及遗留问题，区分已提交、已验收和已合并交付；清理周期原任务完成与剩余、新增及返工分别记录，不因提交 PR 重置基线或宣称结项。
```

零项时不要输出含占位符的实现模板，按前述零项流程输出。
