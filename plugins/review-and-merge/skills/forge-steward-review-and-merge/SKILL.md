# Review And Merge

## 授权与范围

按主线优先级审查本轮开始时已经开放的 Change Request，并在满足条件时合并。Change Request 是平台无关术语，包括 GitHub Pull Request、GitLab Merge Request 等等价对象。

用户明确调用本技能（包括仅选择技能、不附加 prompt）时，默认任务是：冻结 → 审查 → 对满足合并判定的 Change Request 直接合并 → 结项与清理。审查范围、意见分类、Review 轮次、合并判定和结项以本技能为准，不采用仓库另行规定的同类工作流规则；合并方式、必要检查与审批、分支保护、语言和模板等项目约定仍按仓库执行。明确调用即构成满足条件后合并的授权，审查通过后直接执行合并，不再暂停请求用户逐项确认，也不因切换会话要求重复授权。用户本轮的明确限制优先：要求仅审查、不合并或只处理指定项时遵守该边界。自动选中本技能、引用技能名称或询问用法，不构成合并授权。不要绕过分支保护、必要审批或平台权限，不要为了获得全绿结果修改 Change Request 的代码。本轮不自动纳入冻结后新出现的 Change Request。

## 冻结与排序

1. 读取当前仓库规范、既定主线和上轮交接，识别托管平台、默认主线、合并策略和任务层级规则。沿用清理周期期初 task 清单、未完成范围及退出条件，不随本轮清单刷新重置目标。
2. 获取开放 Change Request 完整列表，记录冻结时间、每项 base、head 提交和状态。之后出现的新项只记录，不加入本轮。
3. 根据里程碑、父任务、依赖关系和仓库明确优先级排列；无明确规则时再参考创建时间和解阻价值。不要用编号大小替代主线判断。

## 逐项审查

对冻结清单中的每项执行以下检查：

1. 读取关联 Issue、父子任务、原始范围、逐条验收、保证与非保证、历史讨论、既有 Review 意见和已接受边界。跨仓关联使用原任务完整链接和该仓结项规则，不复制任务；关联不明时记录缺口，不猜测应关闭的编号。
2. 首次审查核对完整 diff、受影响路径、生成文件、迁移、公开契约和测试变化。复审先核对历史证据覆盖的 base/head、已解决意见和已接受边界，审查增量及未解决项，并确认原验收证据在当前 base/head 上仍有效；缺少可信证据或相关代码、契约发生变化时补审受影响范围。不能只看新增 commit 忽略主线变化，也不因换会话重开已解决问题；新证据推翻旧结论时明确记录原因。
3. 核验作者提供的验证证据，并运行与变更风险相称且当前环境适用的检查。CI 全绿只是证据之一，不能替代范围和验收核对；环境不适用的检查必须明确说明，不能伪造通过。
4. 逐条判断验收条件。区分范围内阻塞问题、独立既有缺陷和非保证改进建议：
   - 范围内阻塞问题必须指向具体验收或保证，附证据和可验证的修复条件，暂不合并；必要平台门禁单独记录，不能冒充代码缺陷。
   - 独立既有缺陷先检索去重，再按仓库规范登记或提出分诊建议，不阻塞本项，除非它直接破坏本次验收或构成需立即处置的严重风险。风险例外须写明触发条件、实际影响、处置及恢复交付的条件，不能仅贴“严重”标签。
   - 非保证建议不要求在本项实施，也不阻塞合并；Review 轮次不因更换会话或 Agent 重新计算。已接受的非保证没有新证据或范围变化时不反复登记为 bug。
   - 范围争议确需外部裁决时，记录具体分歧、决策人及解除条件；已明确属于范围外的建议不得继续列为代码必修项。仍有效的平台审批或保护限制单独报告，不自行绕过。
   - 关联的是 tracker，或实际范围达到 feature 级（三个或以上公共协议面、三个或以上有状态产物，或耦合事务与并发、数据迁移、敏感数据流、能力启用中的多个领域）而原 Issue 是单一 task 时，列为范围内阻塞，不合并。
5. 一次完整审查并给出结论计为一轮，复审计入下一轮。进入第三轮时，先逐 commit 审计范围和语义闭合：不能追溯到原验收的改动列为范围内阻塞，要求移出并另行登记；复杂协议或状态任务核对语义模型、持久化关联、外部输入、敏感数据流和能力启用是否闭合。第三轮之后仍反复出现跨文档、跨状态或跨数据流矛盾时不合并，在原 Issue 和 Change Request 记录矛盾，按授权撤销原 Issue 的 ready 状态，交回准备阶段拆分或重建语义模型；每个 commit 都能追溯到验收，不构成继续维持原范围的理由。

## 合并判定

只有同时满足以下条件才可合并：

- 原范围内的验收条件逐条成立。
- 所有适用的必要检查通过，或仓库规则明确允许的例外已经记录并获授权。
- 没有尚未解决的范围内阻塞意见。
- 必要审批、冲突状态和分支保护满足仓库政策。
- 合并前重新获取的 head 提交与完成审查时一致；若发生变化，先审查新增差异和受影响验证。

满足以上条件时立即执行合并，不等待用户再次确认；不满足时不合并，并记录未满足的条件。使用仓库规定的合并方式。没有规定时使用平台和仓库默认方式，不主动使用管理员绕过、强制推送或平台的自动合并排队（auto-merge），审查通过后由本技能直接执行合并。权限、保护规则或平台故障阻止合并时，记录具体原因，不将其报告为已合并。

## 合并后结项

1. 重新读取远端合并状态和目标分支结果，再核对关联任务是否正确完成；仅在验收实际满足且仓库流程允许时关闭任务。跨仓任务不得假设自动关闭，须检查原仓实际状态；缺少权限时交接具体结项动作，无关联任务则明确报告。
2. 检查直接父任务的子项、父级验收及相关未解决缺口；父级完成后再逐层向上核对。仍有未完成范围时写明剩余项及归属，到此停止，不因子项全关就关闭父项，也不借结项开展全仓审计。
3. 清理由本轮创建且已无用途、没有未提交改动或未保存独有提交的 worktree 和本地分支。远端源分支只有在已合并、确认不再复用且仓库策略或用户授权允许时才能删除；来源不明的环境不删除。
4. 每项结束后按下述格式交接，包括未合并或受阻项；确认当前项状态后继续冻结清单，不为新增可选建议延长本轮。

## 交接记录

沿用已有 tracker、任务或仓库指定记录位置，保留一份当前状态；仅在授权范围内写入，没有可写位置时在输出中提供可直接交接的完整记录，不自行创建 tracker。字段按实际填写：清理周期基线与主线；task/Change Request 完整链接、实现仓库及主线；审计基线、覆盖范围与证据位置；当前 head、逐条验收证据；意见分类、Review 轮次、已解决意见与已接受边界；阻塞、下一步及解除条件。缺失项标明未知或不适用，不推定验收通过或将轮次归零。记录实际合并和 task/父级结项状态；期初 task 实际交付及剩余、新增、返工和父级结项分开计数，拆分、迁移、重复或不计划关闭不冒充功能交付，未知计数不推测。

## 输出

处理完整个冻结清单后，用中文汇总：

- 冻结基线和处理顺序。
- 每个 Change Request 的审查结论及证据。
- 实际执行的 Review、合并、关闭和清理操作；明确区分已审查、已批准、已合并和未合并。
- 关联任务及父级的结项状态和未完成差额。
- 新发现问题的去重与分诊结果。
- 清理周期原任务完成及剩余、新增、返工、父级结项和解除的阻塞；已关闭任务的验收遗漏回链原任务及原 Change Request，作为返工记录。
- 尚存阻塞、已接受边界和下一步。

不要自动纳入新增 Change Request，不以 CI 全绿冒充验收成立，也不要把未成功的合并写成已交付。
