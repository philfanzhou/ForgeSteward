## 冻结与排序

1. 读取当前仓库规范、既定主线和上轮交接，识别托管平台、默认主线、合并策略和任务层级规则。沿用清理周期期初 task 清单、未完成范围及退出条件，不随本轮清单刷新重置目标。
2. 获取开放 Change Request 完整列表，记录冻结时间、每项 base、head 提交和状态。之后出现的新项只记录，不加入本轮。调用方说明仍由其他流程处理（例如正在实现或修复）的项，本轮跳过并在输出列明，不审查、合并、评论或加标签。
3. 处理多轮往返项。一轮往返指：该 Change Request 上出现要求修改的 Review Feedback（包括请求修改的审查、Comment、Discussion 或 Review Thread），作者随后推送新提交作出回应；只为同步主线的推送不算。依据平台时间线及交接记录中的 Review 轮次计数，二者不一致时取较大值，不因换会话归零。恰好完成第 3 轮修复推送、当前 head 尚无终审结论的项允许一次终审：按完整合并门禁审查，满足时合并；仍有范围内必修问题时记录当前 head、终审证据和暂停原因，将该项留给人工，不再自动要求第 4 次修复。已记录本 head 终审未通过的项，以及超过 3 轮而未获用户本轮明确点名的项，排除出本轮冻结清单：不重复审查、合并、评论或加标签，只在输出记录链接、轮次及依据。终审仅等待必要 CI、审批或保护条件时保留平台等待状态；条件变化后可复核门禁，不重开代码终审或增加修复轮次。无法确定轮次时按正常流程审查，并标明轮次未知。用户本轮明确点名要求处理该项时除外。
4. 根据里程碑、父任务、依赖关系和仓库明确优先级排列；无明确规则时再参考创建时间和解阻价值。不要用编号大小替代主线判断。

## 逐项审查

对冻结清单中的每项执行以下检查：

1. 读取关联 Issue、父子任务、原始范围、逐条验收、保证与非保证、历史讨论、既有 Review 意见和已接受边界。跨仓关联使用原任务完整链接和该仓结项规则，不复制任务；关联不明时记录缺口，不猜测应关闭的编号。
2. 首次审查核对完整 diff、受影响路径、生成文件、迁移、公开契约和测试变化。复审先核对历史证据覆盖的 base/head、已解决意见和已接受边界，审查增量及未解决项，并确认原验收证据在当前 base/head 上仍有效；缺少可信证据或相关代码、契约发生变化时补审受影响范围。不能只看新增 commit 忽略主线变化，也不因换会话重开已解决问题；新证据推翻旧结论时明确记录原因。上次审查结论可从交接记录或平台审查记录读取，且此后 head、未解决意见和必要检查状态都没变、主线也没有触及该项相关代码或契约的变化时，沿用该结论，只重新确认会随时间变化的合并判定（检查、审批、冲突、分支保护），不重做审查；任一项有变化或读不到上次结论时按上述复审执行，审查标准不变。
3. 核验作者提供的验证证据，并运行与变更风险相称且当前环境适用的检查；CI 已在当前 head 上通过的同一检查不在本地重跑，只补跑 CI 未覆盖而验收需要的检查。CI 全绿只是证据之一，不能替代范围和验收核对；环境不适用的检查必须明确说明，不能伪造通过。必要检查仍在运行时先审查清单中的其他项，最后回来复核；等待上限取该仓库同一检查最近几次成功运行中最长耗时的 2 倍，查不到历史时为 30 分钟。上限内完成且满足全部合并判定的当场合并；超过上限或迟迟未开始运行时记为等待外部检查，不原地空等。
4. 逐条判断验收条件。区分范围内阻塞问题、独立既有缺陷和非保证改进建议：
   - 范围内阻塞问题必须指向具体验收或保证，附证据和可验证的修复条件，暂不合并；必要平台门禁单独记录，不能冒充代码缺陷。
   - 独立既有缺陷先检索去重，再按仓库规范登记或提出分诊建议（同类缺陷归并到已有或同一个 Issue 追加证据，只有已确认可复现、独立且无同类登记的缺陷才新建；可选改进只在原 Issue 或 Change Request 记录，不新建），不阻塞本项，除非它直接破坏本次验收或构成需立即处置的严重风险。风险例外须写明触发条件、实际影响、处置及恢复交付的条件，不能仅贴“严重”标签。
   - 非保证建议不要求在本项实施，也不阻塞合并；Review 轮次不因更换会话或 Agent 重新计算。已接受的非保证没有新证据或范围变化时不反复登记为 bug。
   - 与主线冲突，或仓库要求分支保持最新而已落后：记为需要同步主线，交由修复流程在原分支同步；不当作外部等待，也不作为 Review 往返的修改要求。本技能不自行同步或修改代码。
   - 范围争议确需外部裁决时，记录具体分歧、决策人及解除条件；已明确属于范围外的建议不得继续列为代码必修项。仍有效的平台审批或保护限制单独报告，不自行绕过。
   - 关联的是 tracker，或实际范围达到 feature 级（三个或以上公共协议面、三个或以上有状态产物，或耦合事务与并发、数据迁移、敏感数据流、能力启用中的多个领域）而原 Issue 是单一 task 时，列为范围内阻塞，不合并。
5. 已完成 2 轮往返（定义见「冻结与排序」第 3 步）的 Change Request，本次审查先逐 commit 审计范围和语义闭合：不能追溯到原验收的改动列为范围内阻塞，要求移出并另行登记；复杂协议或状态任务核对语义模型、持久化关联、外部输入、敏感数据流和能力启用是否闭合。每个 commit 都能追溯到验收，不构成维持 feature 级范围的理由。第 3 轮推送后的终审也执行这项审计；修复阶段已记录覆盖其推送 head 的逐 commit 审计时，终审逐条核对记录中每个 commit 与验收的对应是否成立，并完整审计此后新增的 commit，不另起一份重复审计；终审结果按第 3 步持久交接。
