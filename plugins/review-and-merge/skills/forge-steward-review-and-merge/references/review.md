## 冻结与排序

1. 读取当前仓库规范、既定主线和上轮交接，识别托管平台、默认主线、合并策略和任务层级规则。沿用清理周期期初 task 清单、未完成范围及退出条件，不随本轮清单刷新重置目标。
2. 获取开放 Change Request 完整列表，记录冻结时间、每项 base、head 提交和状态。之后出现的新项只记录，不加入本轮。
3. 排除多轮往返项。一轮往返指：该 Change Request 上出现要求修改的 Review Feedback（包括请求修改的审查、Comment、Discussion 或 Review Thread），作者随后推送新提交作出回应。依据平台时间线及交接记录中的 Review 轮次计数，二者不一致时取较大值，不因换会话归零。已达到 3 轮或以上的项说明原始范围本身存在问题，直接排除出本轮冻结清单，等待人工处理：不审查，不合并，不发表 Review 或评论，不添加标签，也不关闭。只在输出中记录链接、轮次及计数依据。无法确定轮次时按正常流程审查，并标明轮次未知。用户本轮明确点名要求处理该项时除外。
4. 根据里程碑、父任务、依赖关系和仓库明确优先级排列；无明确规则时再参考创建时间和解阻价值。不要用编号大小替代主线判断。

## 逐项审查

对冻结清单中的每项执行以下检查：

1. 读取关联 Issue、父子任务、原始范围、逐条验收、保证与非保证、历史讨论、既有 Review 意见和已接受边界。跨仓关联使用原任务完整链接和该仓结项规则，不复制任务；关联不明时记录缺口，不猜测应关闭的编号。
2. 首次审查核对完整 diff、受影响路径、生成文件、迁移、公开契约和测试变化。复审先核对历史证据覆盖的 base/head、已解决意见和已接受边界，审查增量及未解决项，并确认原验收证据在当前 base/head 上仍有效；缺少可信证据或相关代码、契约发生变化时补审受影响范围。不能只看新增 commit 忽略主线变化，也不因换会话重开已解决问题；新证据推翻旧结论时明确记录原因。
3. 核验作者提供的验证证据，并运行与变更风险相称且当前环境适用的检查。CI 全绿只是证据之一，不能替代范围和验收核对；环境不适用的检查必须明确说明，不能伪造通过。
4. 逐条判断验收条件。区分范围内阻塞问题、独立既有缺陷和非保证改进建议：
   - 范围内阻塞问题必须指向具体验收或保证，附证据和可验证的修复条件，暂不合并；必要平台门禁单独记录，不能冒充代码缺陷。
   - 独立既有缺陷先检索去重，再按仓库规范登记或提出分诊建议（同类缺陷归并到已有或同一个 Issue 追加证据，只有已确认可复现、独立且无同类登记的缺陷才新建；可选改进只在原 Issue 或 Change Request 记录，不新建），不阻塞本项，除非它直接破坏本次验收或构成需立即处置的严重风险。风险例外须写明触发条件、实际影响、处置及恢复交付的条件，不能仅贴“严重”标签。
   - 非保证建议不要求在本项实施，也不阻塞合并；Review 轮次不因更换会话或 Agent 重新计算。已接受的非保证没有新证据或范围变化时不反复登记为 bug。
   - 范围争议确需外部裁决时，记录具体分歧、决策人及解除条件；已明确属于范围外的建议不得继续列为代码必修项。仍有效的平台审批或保护限制单独报告，不自行绕过。
   - 关联的是 tracker，或实际范围达到 feature 级（三个或以上公共协议面、三个或以上有状态产物，或耦合事务与并发、数据迁移、敏感数据流、能力启用中的多个领域）而原 Issue 是单一 task 时，列为范围内阻塞，不合并。
5. 已完成 2 轮往返（定义见「冻结与排序」第 3 步）的 Change Request，本次审查先逐 commit 审计范围和语义闭合：不能追溯到原验收的改动列为范围内阻塞，要求移出并另行登记；复杂协议或状态任务核对语义模型、持久化关联、外部输入、敏感数据流和能力启用是否闭合。每个 commit 都能追溯到验收，不构成维持 feature 级范围的理由。往返达到 3 轮后不再由本技能处理，按第 3 步排除。
