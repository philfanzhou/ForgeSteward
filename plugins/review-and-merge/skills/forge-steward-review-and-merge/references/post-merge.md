## Complete tasks after merging

Explicitly provide merge-commit title/body under repository commit-message rules (language, format, Change Request/Issue references), including squash merges. Do not copy the Change Request body by default. Use platform defaults when repository rules are absent.

1. Read back remote merged status and target-branch results, then verify linked tasks. Close only when acceptance is actually met and repository process permits. Cross-repository tasks may not auto-close; check their original repository. Without permissions, hand off concrete closure actions. Explicitly report no linked tasks when applicable.
2. Check direct-parent children, parent acceptance, and related unresolved gaps; only after the parent is complete proceed upward. If scope remains, record remaining items/ownership and stop. All children closed does not itself justify parent closure, nor a repository-wide audit.
3. Update local mainline: if the branch exists, fetch then run `git merge --ff-only <remote>/<mainline>` (such as `origin/main`) in a clean workspace with mainline checked out. This command affects the checked-out branch; never run it on another branch. If mainline's workspace is dirty or cannot fast-forward, preserve it and report, without reset/overwrite.
4. Delete the merged request's local source branch when it is safely deletable, and remove its dedicated worktree only when it meets every condition in [Leftover branch cleanup](branch-cleanup.md#worktrees), whether created this round or earlier. For the branch, confirm local head equals merged Change Request head (no unique unpushed commits), neither default nor protected, and no open request uses it. For attached worktrees, require no uncommitted or untracked files, unlocked, not current or caller-listed active, no other flow using it, and either the conventional directory or the caller-supplied run ownership record names this exact worktree path. Never infer ownership from a path alone; leave unrecorded external locations untouched. Before considering detached removal, read [Disposable detached workspaces](detached-workspaces.md) in full and satisfy its additional ownership, completion, evidence, recovery, and final-check requirements. Ordinary Git worktrees use `git worktree remove`, never `--force`; host-managed workspaces use only supported archive/lifecycle APIs with metadata readback. If current, first switch to mainline's workspace under step 3, then recheck every condition. Otherwise retain and report the failed condition. A refused `git branch -d` does not prove unmerged status: squash/rebase may leave source commits outside mainline. Use merged status and matching head; force-delete the local branch once verified. After ordinary Git worktree removal, run `git worktree prune`.
5. Check automatic post-merge source-branch deletion (for example GitHub's setting, GitLab's default, or that Merge Request's option), then read actual remote branch state. The setting is diagnostic only; do not change it. Reuse it within one invocation instead of rereading after each merge, but check every branch's actual state. Record platform deletions. If still present, delete only this repository's merged source branch after rechecking that remote head equals the merged request head, it is neither default nor protected, and no other open request uses it; then read back. Disabled/unreadable settings do not block safe checks/cleanup. Retain forks, unknown sources, changed heads, shared branches, or uncertain protection and report reasons. On deletion failure, record error/retained branch and continue. Honor explicit user branch-retention requests.
6. Hand off every item, including unmerged/blocked items, under [Handoff records](handoff.md). Confirm state and continue the frozen list without extending this round for optional suggestions.
