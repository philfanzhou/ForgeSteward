# Review And Merge

## 授权与范围

按主线优先级审查本轮开始时已经开放的 Change Request，并在满足条件时合并。Change Request 是平台无关术语，包括 GitHub Pull Request、GitLab Merge Request 等等价对象。

只有用户当前请求明确授权“满足条件后合并”时才执行合并；不能从 Skill 名称或隐式触发推定授权。不要绕过分支保护、必要审批或平台权限，不要为了获得全绿结果修改 Change Request 的代码。本轮不自动纳入冻结后新出现的 Change Request。

## 冻结与排序

1. 读取当前仓库规范，识别托管平台、默认主线、合并策略和任务层级规则。
2. 获取开放 Change Request 完整列表，记录冻结时间、每项 base、head 提交和状态。之后出现的新项只记录，不加入本轮。
3. 根据里程碑、父任务、依赖关系和仓库明确优先级排列；无明确规则时再参考创建时间和解阻价值。不要用编号大小替代主线判断。

## 逐项审查

对冻结清单中的每项执行以下检查：

1. 读取关联 Issue、父子任务、原始范围、逐条验收、保证与非保证、历史讨论、既有 Review 意见和已接受边界。
2. 核对完整 diff、受影响路径、生成文件、迁移、公开契约和测试变化。只扩展到证明本次变更正确性所必需的相邻代码，不扩大为独立审计。
3. 核验作者提供的验证证据，并运行与变更风险相称且当前环境适用的检查。CI 全绿只是证据之一，不能替代范围和验收核对；环境不适用的检查必须明确说明，不能伪造通过。
4. 逐条判断验收条件。区分范围内阻塞问题、独立既有缺陷和非保证改进建议：
   - 范围内阻塞问题必须留下可操作的明确意见，暂不合并。
   - 独立既有缺陷先检索去重，再按仓库规范登记或提出分诊建议，不阻塞本项，除非它直接破坏本次验收或构成严重风险。
   - 非保证建议只在仓库既定 Review 预算内处理，不因更换会话或 Agent 重新计算预算，也不要求消除所有改进空间。

## 合并判定

只有同时满足以下条件才可合并：

- 原范围内的验收条件逐条成立。
- 所有适用的必要检查通过，或仓库规则明确允许的例外已经记录并获授权。
- 没有尚未解决的范围内阻塞意见。
- 必要审批、冲突状态和分支保护满足仓库政策。
- 合并前重新获取的 head 提交与完成审查时一致；若发生变化，先审查新增差异和受影响验证。

使用仓库规定的合并方式。没有规定时使用平台和仓库默认方式，不主动使用管理员绕过、强制推送或自动合并。权限、保护规则或平台故障阻止合并时，记录具体原因，不将其报告为已合并。

## 合并后结项

1. 核对关联任务是否因合并正确完成；仅在验收实际满足且仓库流程允许时关闭任务。
2. 从直接任务开始逐层检查父任务。父级仍有未完成范围时写明差额，不提前关闭，也不扩展实现。
3. 清理由本轮创建且已无用途的干净 worktree 和本地分支。远端源分支只有在已合并、确认不再复用且仓库策略或用户授权允许时才能删除；不得删除含未提交改动或来源不明的环境。
4. 切换到下一项前，在运行记录中保存结论、Review 轮次、已解决意见、已接受边界、任务结项状态和待办。只有仓库指定了持久记录位置且当前请求允许写入时，才发布平台评论或更新任务。

## 输出

处理完整个冻结清单后，用中文汇总：

- 冻结基线和处理顺序。
- 每个 Change Request 的审查结论及证据。
- 实际执行的 Review、合并、关闭和清理操作；明确区分已审查、已批准、已合并和未合并。
- 关联任务及父级的结项状态和未完成差额。
- 新发现问题的去重与分诊结果。
- 尚存阻塞、已接受边界和下一步。

不要自动纳入新增 Change Request，不以 CI 全绿冒充验收成立，也不要把未成功的合并写成已交付。
