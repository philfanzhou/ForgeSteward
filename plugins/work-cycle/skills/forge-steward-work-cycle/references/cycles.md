## Work cycles and subagent handoffs

Run at most the user's positive-integer cycle count, default 10. A cycle begins with a nonempty prepare-work result and includes that list's execution, review, required repairs, and re-review; it is not a Change Request's review-round count. Create a new subagent per stage with explicit skill, target repository, prior persisted results, full delivery authorization, and [Return format](subagent-lifecycle.md#return-format). Subagents must read original Issues/Change Requests, repository rules, and skill references, not implement from the orchestrator's summary. Also state that no one will answer them immediately: record user questions/clarifications in original Issues/Change Requests and returned results, then continue independent work rather than waiting. Apply each skill's time limits to CI, environment builds, and external replies; after timeout, record status and return instead of waiting idly. Await complete results, check actual remote state of affected objects, save handoffs, and release closable completed threads under [Lifecycle and recovery](subagent-lifecycle.md) before dependent dispatch. Where supported, [Move completed items forward](concurrency.md) allows handed-off requests into review early and review/repair alongside later execution/preparation. The following order expresses per-item and per-cycle dependencies.

After startup checking, read open Change Requests. If nonempty, immediately dispatch review-and-merge to handle its entire frozen queue and necessary repairs/re-review under steps 3–4, verifying merge/cleanup results. Complete this queue even with no preparable Issues. Do not dispatch review for an empty list. Startup queue processing does not count as a cycle. Persist paused/waiting items and retain original review rounds/final-review decisions in later cycles; refreezing must not reset or cause idle loops.

1. Dispatch prepare-work. Its final output is only its single-line Issue list or `[]`. On `[]`, stop all later cycles without empty execution tasks and read the stage's `result.md` for the reason to record as the final report's `stop_reason`; still list paused/waiting requests in [Final report](report.md). Forward a nonempty list unchanged and in order to execution, preserving Issue evidence locations. Read the prepare-work stage's `result.md` from its `run_record.py task-dir` directory for batch relationships and queued resources, and record them in the scheduling table. The stage reply itself stays one line. For cycle 2 onward, provide earlier preparation-record locations so unchanged evidence can be reused.
2. Dispatch execute-work for the full list, or one subagent per Issue under [Move completed items forward](concurrency.md). Implement in original order and submit independent Change Requests. A genuinely blocked item does not shrink the list or block independent later work. Verify each original Issue, implementation PR/MR, verification, and unfinished status.
3. Dispatch review-and-merge for the full open queue it freezes at invocation, not only this cycle's new PRs/MRs. With concurrency, dispatch per-request review/repair under [Move completed items forward](concurrency.md), merging one at a time. Skip only items identified as owned by another stage. Merge directly when original acceptance, checks, approvals, and protection pass; verify branch cleanup. This dispatch carries the user's full orchestration authorization without per-item questions. Send required findings or mainline conflicts to a fix-feedback subagent for original-branch repair/push, then create a new reviewer. If only behind under a current-branch policy, use review-and-merge's merge lane under [Move completed items forward](concurrency.md). Continue repair → new review while repairable in-scope feedback or sync remains, until merged, paused after failed third-repair final review, waiting only on external conditions, or genuinely blocked. Each review/repair invocation freezes its own queue; do not inject later items. Classify CI/approval-only waits without fabricating repairs/merges.
4. Preserve each request's rounds from platform history/handoffs across cycles and subagents. After the third repair push, allow one final review: merge if all conditions pass; otherwise pause only that Issue/request for human action when required in-scope issues remain. No fourth automatic repair or another review. Other requests and later independent Issues continue. Dependencies on its unmerged code remain subject to preparation/execution prerequisite rules.
5. At cycle end, record actual remote results, reasons, and next actions in [Final report](report.md)'s fields/vocabulary. Independent repair/review continues; one merge or pause does not end the whole round. The next cycle begins with new prepare-work (under concurrency it may start after execution without waiting for review/repair loops). That skill determines its frozen queue/backlog priority; the orchestrator does not add Issues.

## Persistence and stopping

Reuse stage trackers and persisted Issue/Change Request evidence. Also keep a short orchestration handoff: repository/mainline, requested count, completed/current cycles, each cycle's original Issue list and PR links, heads, acceptance/check state, review rounds, paused items, external checks/approvals, and next actions. Save it under [Run records and timing](run-record.md) and also update existing authorized records when writable. If neither is writable, provide it in conversation handoff/final output without claiming persistence. After compaction restore it and required current-stage rules; never duplicate PRs or reset counts.

Tell each review-and-merge dispatch to skip leftover branch cleanup. Before run completion, once no other stages remain active, dispatch a review-and-merge subagent solely for leftover cleanup, giving retained branches/workspaces such as paused/external-wait items. Do not dispatch after an explicit user stop.

After startup-queue handling, end at cycle limit, prepare-work `[]`, or explicit stop. Low/near-limit quota warnings do not justify ending, reducing cycles, or skipping stages. Actual required create/wait failures first use [Lifecycle and recovery](subagent-lifecycle.md) for status checks, available recovery, and bounded retries. End with handoff only for confirmed missing required capability or exhausted recovery, not one warning/failure. Continue independent work around blockers. If only external waits/pauses remain, record each release condition without idle waiting or counting unmerged work as delivered. Record startup/cycle original Issues, Change Requests, actual merges, pause reasons/remainder, leftover cleanup, and check-workflow run/skip with cache version/time in [Final report](report.md), then generate it. Startup checking is not a cycle. Scheduled restarts outside this conversation require an external scheduler; the skill claims no background scheduling capability.
