## 工作周期与子 Agent 交接

最多运行用户指定的正整数个工作周期，默认 10。一个周期从非空的 `prepare-work` 结果开始，涵盖该清单的执行、审查、必修反馈修复及复审；它不是 Change Request 的 Review 往返轮数。每个阶段创建新的子 Agent，明确给出要调用的技能、目标仓库、上一阶段的持久化结果和本次完整交付授权。子 Agent 自己读取原 Issue/Change Request、仓库规则及其技能引用文件，不能只依据编排 Agent 的摘要实施。派发时同时说明：本次没有人会即时回答子 Agent 的提问，需要用户回答或澄清的问题写进原 Issue/Change Request 和返回结果，再继续其他独立工作，不停下等待答复；等待 CI、环境构建或外部回复按阶段技能的等待上限处理，超过上限记录状态后交回结果，不原地空等。阶段结束后等候完整结果，核对该阶段涉及的 Issue 和 Change Request 的实际远端状态，按 [生命周期与恢复规则](agents.md) 保存交接并释放可关闭的已完成线程，再派发下一阶段。运行时支持时，按 [已完成项先往下走](concurrency.md) 让已交出的 Change Request 提前进入审查，并让审查与修复的循环和后续执行、准备同时进行；以下顺序是每个 Change Request 和每个周期各自的依赖顺序。

启动检查完成后，只读获取当前开放 Change Request 列表。非空时立即派发 `review-and-merge` 子 Agent，按下文第 3、4 步处理其冻结的完整队列及必要修复、复审，核对合并与清理结果；即使没有可准备的 Issue，也须完成此队列。空列表不派发审查。启动队列处理不计入工作周期；其暂停、等待项记入交接，后续周期审查时沿用原 Review 轮数和终审结论，不因重复冻结而重置或空转。

1. 派发 `prepare-work` 子 Agent。其最终输出只能是技能约定的一行 Issue 列表或 `[]`。收到 `[]` 时结束全部后续周期，不创建空执行任务；已有暂停或等待中的 Change Request 仍须在最终报告列明。非空列表按原顺序原样交给执行子 Agent，并保存 Issue 中的准备证据位置。第 2 个及以后周期派发准备时，告知本次运行前面周期的准备记录位置，供其沿用未变化部分。
2. 派发 `execute-work` 子 Agent 处理完整列表；支持并发时按 [已完成项先往下走](concurrency.md) 每个 Issue 派一个子 Agent。它按原顺序逐项实现并提交独立 Change Request；单项真实阻塞不缩减原列表，也不阻断独立后项。核对每项的原 Issue、实现 PR/MR、验证和未完成状态。
3. 派发 `review-and-merge` 子 Agent 审查该技能在本次调用开始时冻结的完整开放 Change Request 队列，不自行缩成仅审本周期新建的 PR/MR，只跳过编排告知仍由其他阶段持有的项；满足原验收、检查、审批和保护要求时直接合并，并核对合并后分支清理。此显式派发承接用户对编排 Skill 的完整交付授权；不逐项询问。初审或复审发现必修项，或有 Change Request 需要同步主线（与主线冲突，或仓库要求分支保持最新而已落后）时，交给 `fix-feedback` 子 Agent，在原分支修复并推送，然后派发新的审查子 Agent。只要仍有可修的范围内必修反馈或需要同步主线的项，就按修复 → 新审查继续，直到各项合并、第三次修复后的终审未通过而暂停、仅剩外部门禁等待或出现具体真实阻塞。每次审查和修复仍各自冻结本次队列，不把冻结后新项塞进当前调用；仅等待 CI/审批、无需代码修改的项按阶段技能分类，不伪造修复或合并。
4. 同一 Change Request 的 Review 往返轮数沿用平台时间线和交接记录，不因本技能周期或子 Agent 更换归零。第三次修复推送后允许一次终审：全部条件满足就合并；仍有范围内必修问题则仅将该 Issue/Change Request 标为暂停、待人工处理，不再自动进行第四次修复或另一轮审查。它不阻断其他 Change Request 的审查、修复、合并，也不阻断下一周期的独立 Issue。依赖其未合并代码的 Issue 仍按 prepare/execute 的前置门禁处理。
5. 一周期结束时，对每项记录最终状态：已合并、待审查/等待平台必需检查或审批、具体外部阻塞、或三轮后暂停。修复和审查可以按独立项继续，不能因为首个 PR 合并或某个 PR 暂停就结束整轮。下一周期从新一次 `prepare-work` 开始（同时运行时，执行阶段结束即可派发，不必等本周期的审查和修复循环结束），其冻结队列和存量优先级仍由该技能决定；编排 Agent 不自动给它补新 Issue。

## 持续性和停止条件

沿用各阶段已有 tracker、Issue 和 Change Request 的持久证据。编排 Agent 另保留短交接：目标仓库与主线、请求轮数、已完成/当前周期、每周期原 Issue 清单与 PR 链接、head、验收和检查状态、Review 往返次数、已暂停项、仍在等待的外部检查或审批、下一动作。能写入既有授权记录时更新；没有可写位置则在会话交接和最终输出提供，不虚构已持久化。上下文压缩后恢复该记录和当前阶段的必需规则，不重复创建 PR 或重置轮数。

启动存量队列处理完毕后，达到轮数上限、`prepare-work` 返回 `[]` 或用户明确停止时结束。额度较低或接近限制的提示不构成终止条件，不据此缩减请求轮数或跳过必需阶段。必需子 Agent 的实际创建或等待调用失败时，先按 [生命周期与恢复规则](agents.md) 核对状态、尝试可用恢复措施及有限重试；仅在确认缺少必需能力，或恢复后仍无法继续时保存交接并结束，不仅凭提醒或一次失败提前结束。一个项受阻时继续可独立的工作；全队列只剩外部等待或暂停项时说明解除条件，不空转等待，也不把未合并项计作交付。最终以中文分别汇总启动队列和各周期的原 Issue、Change Request、实际合并、分支清理、暂停原因和剩余范围；`check-workflow` 的运行或跳过及缓存版本/时间单列，不计入工作周期。当前会话之外的定时重启需要外部调度，技能自身不宣称具备后台定时能力。
