## 已完成项先往下走

目的是不让先完成的项等待整批：工作量、各阶段技能的判定标准、合并条件和 Review 轮数上限都不变，只改变派发时机。

### 启用条件与退回

运行时能在后台运行子 Agent，并能在其运行期间读取其进度（交接记录、消息或状态查询），且[资源锁](verification.md)可用时启用本节；否则按 [轮次、交接与终止](cycles.md) 逐阶段串行，不因此报错或缩减工作。启用后某次后台派发或进度读取失败，先按 [生命周期与恢复](agents.md) 处理；仍无法确认进度时，该部分退回串行，等相关阶段结束后再派发依赖它的工作。

### 可以同时进行的阶段

- `execute-work` 与 `prepare-work` 仍互相串行并保持周期顺序：执行阶段建完本周期全部 Change Request（或确认各项状态）后，才派发下一周期的准备，避免准备阶段选中正在实现、尚无 Change Request 的 Issue。
- `review-and-merge` 与 `fix-feedback` 之间仍互相串行（修复 → 新审查的循环不变），但这条循环可以与执行阶段、下一周期的准备阶段同时进行。启动时已有 Change Request 的处理也可与第 1 周期的准备同时进行。
- 同一时刻每类阶段最多一个子 Agent；不同周期的阶段可以重叠，周期计数和停止条件仍按 [轮次、交接与终止](cycles.md)。

### 一个 Change Request 同一时间只归一个阶段

编排 Agent 维护持有表：每个 Change Request 当前由哪个阶段处理。

- 执行阶段完成某项的验证并处理完本项 CI 后，在交接记录中标明该 Change Request 已交出；交出前它归执行阶段，交出后执行阶段不再向其分支推送，后续修改只经审查和修复。
- 派发审查或修复时，明确列出仍由其他阶段持有的 Change Request；阶段技能本轮跳过这些项并在输出列明，不审查、合并、评论或推送。审查开始后才交出的项，不塞进这次审查，留给下一次审查派发。
- 有已交出但未审查的 Change Request，且没有审查或修复子 Agent 在运行时，派发新的审查子 Agent。合并前重新获取 head 并与审查时比对的规则继续作为兜底。

### 工作目录与 git 操作

- 每个阶段在自己独立的工作区（例如独立 worktree）中工作，不使用用户的主工作目录，不检出其他阶段正在使用的分支。
- 执行阶段只从刚获取的远端主线建立分支，不依赖本地主线；推送和创建 Change Request 前再获取一次远端主线，有冲突先同步再提交。之后才出现的冲突按修复阶段的同步主线规则处理。
- 合并后的本地清理只删除已合并 Change Request 自己的分支和专用工作区，并确认该工作区不是其他正在运行阶段的工作目录；更新本地主线只在没有阶段使用的主线工作区进行。
- 并发阶段的本地验证按[并发时的本地验证](verification.md)隔离和排队。
- 并发 git 操作报告锁冲突时，等待几秒后有限重试；重试仍失败时记录错误交回结果，不删除锁文件，不当作业务失败。

### 共享记录只由编排 Agent 写

同时运行时，tracker 的当前调度段落等共享进度记录只由编排 Agent 写入：派发时告知阶段子 Agent 不写共享记录，把需要写入的内容放进返回结果，由编排 Agent 汇总写入。各阶段照常写自己负责的 Issue 和 Change Request。

### 汇报

最终报告说明本次是否启用同时运行、退回串行的原因，以及多个 Change Request 同时运行 CI 时出现的排队；排队增加的耗时不算作节省的时间。
